## 三、实验整体逻辑分析

### 2.1 本章节的逻辑主线

任务三完成 Buddy System（伙伴系统）物理页分配算法。ucore 通过 `struct pmm_manager` 提供统一的物理内存管理接口，具体分配策略由不同管理器实现。Buddy System 将空闲物理页划分成大小为 `2^k` 页的块，用不同阶的空闲链表进行管理。分配时先寻找可以满足请求的块，需要时从更高阶块分裂；释放时检查同阶伙伴是否空闲，能够合并就继续向上合并。

实验分两部分：第一份提示词用于生成 Buddy 分配模块并接入内核；第二份提示词用于生成 `buddy_check()`，检查分配、释放、页数取整、分裂、合并和边界条件。两部分都通过现有物理内存管理接口与 `pmm.c` 的初始化和检查流程连接。

### 2.2 功能的逐步实现

1. 首先阅读 `pmm.c`、`pmm.h`、`memlayout.h` 和链表接口，明确 Buddy 需要实现的函数及 `Page` 的状态约定，保证分配器能够通过统一管理器接口接入内核。
2. 接着完成 Buddy 分配算法，用多阶空闲链表管理 2 的幂大小的物理页块，实现区间登记、分配时分裂、释放时合并和空闲页统计。
3. 然后完成 `buddy_check()`，先检查普通分配、页数取整、空闲链表和伙伴分裂合并，并建立可恢复的受控测试区域，使需要固定块布局的测试不影响真实空闲链表。
4. 最后补充相同取整结果的合法释放、相邻但非伙伴块、`init_memmap()` 多次登记和三种非法释放断言检查，再结合编译、QEMU 输出及代码状态确认结果。

## [SPECIFICATION]

### 1. buddy_init()
**Pre-Condition**
- 内核已经选择 Buddy 作为管理器。
- 此时尚未通过 Buddy 登记可用物理页。

**Post-Condition**
- 所有k对应的空闲链表初始化完毕，处于空状态。
- 当前空闲页计数置为 0。

**Case 1：正常初始化**
初始化所需的空闲链表和统计状态，供 `init_memmap()` 注册可用页面。

**Requirements**
根据可用物理内存上限来确定最大k。
此函数只初始化 Buddy 的管理状态。

### 2. buddy_init_memmap(struct Page *base, size_t n)
**Pre-Condition**
- Buddy 内部状态已经初始化。
- `base` 指向一个此前未注册的、连续可用的物理页描述符区间`base`，`[base, base + n)` 代表已经由上层确认可用、尚未登记的连续物理页。
- `n > 0`。
- 输入范围不包括内核镜像、OpenSBI、页描述符数组或其他保留区域。

**Post-Condition**
- 全部 `n` 个物理页被登记为空闲页。
- 该区间被变为一个或多个互不重叠、大小为 2 的幂、按自身大小对齐的空闲块。
- 所有被登记的页`flag`除`PG_property`为0，引用计数为 0。
- 每个空闲块头页具有正确的 `PG_property` 状态及 `property` 值。
- 每个空闲块进入其对应 k 的空闲管理结构。
- 空闲页总数增加 `n`，登记过程中不会丢失页面或重复统计页面。

**Case 1：输入只有一个物理页**
当 `n = 1` 时，应登记一个 k = 0 的空闲块，空闲页数增加 1。

**Case 2：区间长度不是 2 的幂**
必须能够将区间划分为多个 2 的幂大小的合法块，而不是丢弃多余页面。
例如输入包含 13 个连续页。不得丢弃多余页面，应拆为若干合法的二次幂块，最终登记页数之和必须为 13。

**Case 3：传入起始位置未按大块对齐**
必须根据物理页号处理对齐。
例如可用区间的物理页号范围为 `[3,16)` 时，可形成大小为 1、4、8 页的合法块，分别为 `[3,4)`、`[4,8)`、`[8,16)`。

**Case 4：多次登记可用区间**
多次调用可登记不同的、不重叠的可用物理页区间。新的登记不能破坏已存在的空闲块。
对于物理位置相邻、大小相同且满足 Buddy 关系的完整空闲块，允许并应能够最终合并。不能越过保留页或未登记区间合并。

**Case 5: 非法输入**
- `n <= 0`
- 有页不为保留页

**Requirements**
- 不允许注册输入区间以外的页。
- 对重叠或重复登记的非法输入应进行检查，不能把同一页重复加入空闲链表。
- 必须使用 base - pages 取得全局下标，而不能把每次登记区间的起点当作新的下标 0

### 3. buddy_alloc_pages(size_t n)

**Pre-Condition**
- Buddy 已完成初始化及必要的物理页登记。
- `n > 0`。
- 各阶空闲管理结构保持一致。

**Post-Condition**
成功时：
- 返回一个有效的 `struct Page *`，指向实际分配块的起始页。
- 返回块包含至少 `n` 个连续物理页，实际块大小是能够容纳 `n` 的最小合法二次幂， `property`为实际块大小，不记录实际申请的块大小，按自身大小对齐。
- 被分配的块不再作为空闲块留在任何k链表中。
- 空闲页总数减少实际分配块的页数，返回块中的首页应从空闲状态转为已分配状态。

失败时返回 `NULL`，且原分配器状态保持不变。

**Case 1：n为非 2 的幂**
应向上取整为能够容纳请求的最小 2 的幂页数。例如 `n=3` 实际保留 4 页，`n=5` 实际保留 8 页。多出的页面属于当前分配块，不能再拆分分配。空闲页计数应按照实际分配块的容量减少。

**Case 2：存在恰好匹配的空闲块**
例如请求 4 页且存在可用的 4 页伙伴块时，可以直接分配该块。
维护头页标记、分配信息及空闲页计数。

**Case 3：只有更大的空闲块**
- 寻找能够满足请求的更高阶且阶数最小的空闲块，并逐级对半拆分，每次拆分后两个子块大小相等，均为父块的一半；
- 未分配出去的伙伴子块继续保持可用，应纳入相应 k 的空闲管理结构，已被拆分的父块不得继续作为一个完整空闲块出现。例如存在 16 页块而申请 4 页时，应能够保留未分配的 12 页供后续使用，但是已经被拆分成4，8。
- 维护头页标记、分配信息及空闲页计数。

**Case 4：没有可满足请求的连续 Buddy 块**
当不存在足够大小的合法空闲块时返回 `NULL`。
这不仅包括总空闲页数不足，也包括虽然总空闲页数足够，但不存在满足请求大小的连续且可合并空闲块。
失败后空闲块结构、页面状态和空闲页统计必须保持不变。

**Case 5：异常参数**

- `n == 0`：使用 `assert` 拒绝非法调用。
- 当 `n` 过大，无法安全地计算向上取整后的 2 的幂大小或者超过 Buddy 所支持的最大块容量时，应返回 `NULL`

**Requirements**
成功返回块的起始物理页号必须满足实际块容量的对齐要求。
每个成功分配的块只有空闲块大小，不记录实际申请的页数。

### 4. buddy_free_pages(struct Page *base, size_t n)

**Pre-Condition**
- `base` 是此前一次成功分配的起始页，对应的分配块尚未被释放。
- `n > 0`，为该次分配的原始请求页数。
- 调用的请求n向上取 2 的幂后，必须与该块记录的实际分配大小一致。
- 不允许从块内部任意位置开始释放，也不允许对为空闲块重复释放。

**Post-Condition**
- 整个原始分配块变为空闲块。
- 若同阶伙伴块空闲，则能够逐级合并。被合并的两个子块不再作为独立块存在，起始物理页号满足对齐要求。
- 维护头页标记、分配信息及空闲页计数，空闲页只增加本次归还的实际页数。

**Case 1：伙伴不存在、未登记或不空闲**
只释放当前块，不进行合并。

**Case 2：两个同阶伙伴均为空闲**
两个块应合并为一个大小翻倍的空闲块。
若合并后的块仍有符合条件的空闲伙伴，应继续向上合并。直到遇到不可合并的伙伴、管理范围边界或最大k。

**Case 3：相邻块并非同阶伙伴**
即使它们物理连续，也不能错误合并。

**Case 4：非 2 的幂请求释放**
n向上取 2 的最小幂。例如 `alloc_pages(3)` 实际占用 4 页，应允许使用 `free_pages(base, 3)` 释放 4 页。

不能只归还 3 页，遗漏的 1 页也不能变成不可管理的内存。

**Case 5：非法释放**
以下操作非法，应通断言或检查拒绝：
- `base == NULL`或者起始页号不是实际分配块大小的整数倍；
- `n == 0`；
- 释放已空闲的块；
- 从已分配块内部开始释放；
- 释放页数与记录的块大小不匹配；
- 释放保留页或未登记页。

### 5. buddy_nr_free_pages()
**Pre-Condition**
Buddy 已经初始化。

**Post-Condition**
直接返回当前真正处于空闲状态的物理页总数。。

**Requirements**
空闲块计数已在对块的操作中更新了。

### 6. buddy_check()

**Pre-Condition**
管理器已初始化且已有合法可用页区间。

**Post-Condition**
进行基本分配、释放及计数检查，检查结束后所有测试用页面均已归还。

**Requirements**
暂不进行实现。
````

## [RELY]
以下为实现测试所需要的最小工程上下文。
**1. 物理内存管理器接口**
`kern/mm/pmm.h` 定义：
```c
struct pmm_manager {
    const char *name;
    void (*init)(void);
    void (*init_memmap)(struct Page *base, size_t n);
    struct Page *(*alloc_pages)(size_t n);
    void (*free_pages)(struct Page *base, size_t n);
    size_t (*nr_free_pages)(void);
    void (*check)(void);
};
```
`pmm.c` 通过全局 `pmm_manager` 指针调用上述接口。

```c
const struct pmm_manager buddy_pmm_manager;
```
其 `.check` 成员绑定 `buddy_check()`。

`pmm.c` 提供统一接口：
```c
struct Page *alloc_pages(size_t n);
void free_pages(struct Page *base, size_t n);
size_t nr_free_pages(void);
```

以及单页接口：
```c
#define alloc_page() alloc_pages(1)
#define free_page(page) free_pages(page, 1)
```

内核初始化流程为：
```
pmm_init() → init_pmm_manager() → page_init() → check_alloc_page()
```
- `init_pmm_manager()`：选择并初始化 Buddy 分配器。
- `page_init()`：完成物理内存探测、保留页排除及空闲页登记。
- `check_alloc_page()`：通过 `pmm_manager->check()` 调用 Buddy 的测试函数。

**2. 物理页描述符**
`kern/mm/memlayout.h` 定义：
```c
struct Page {
    int ref;
    uint64_t flags;
    unsigned int property;
    list_entry_t page_link;
};
```

相关标记：
- `PG_reserved`：表示该物理页被内核保留，不能分配。
- `PG_property`：表示该 `Page` 是一个空闲连续物理块的头页。
- `PageReserved(page)`：检查页面是否被保留。
- `PageProperty(page)`：检查页面是否为空闲块头。
- `page_ref(page)`：获取页面引用计数。

Buddy 中 `property` 的使用约定为：
- 空闲块头的 `property` 保存空闲块实际页数，并设置 `PG_property`。
- 分配成功后，分配块头清除 `PG_property`，但 `property` 仍保存实际分配块的页数，`property` 不保存原始申请页数。
例如申请 3 页：
```c
struct Page *p = alloc_pages(3);
```
如果分配成功，实际占用 4 页，分配块头应满足：
```c
assert(p->property == 4);
assert(!PageProperty(p));
```

**3. 地址转换及物理页范围**
`kern/mm/pmm.h` 提供：
- `pages`：物理页描述符数组起始地址。
- `npage`：物理页号上界。
- `nbase`：DRAM 起始物理页号。
- `page2ppn(page)`：获取物理页号。
- `page2pa(page)`：获取物理地址。
- `pa2page(pa)`：获取物理页描述符。
其中：
```c
page2ppn(page) = page - pages + nbase
```
页面大小为：
```c
#define PGSIZE 4096
#define PGSHIFT 12
```
对于成功分配的 `Page *p`，若实际块大小为 `size` 页，应满足：
- `nbase <= page2ppn(p) < npage`。
- `size <= npage - page2ppn(p)`。
- `page2ppn(p) % size == 0`。
- 分配块中的页不属于保留页。
实际块大小始终是 2 的幂。

**4. 多阶空闲链表**
Buddy 使用多阶空闲链表管理空闲块。
第 `k` 阶链表存放大小为 `2^k` 页的空闲块。
`libs/list.h` 提供：
- `list_entry_t`
- `list_init()`
- `list_empty()`
- `list_next()`
- `list_prev()`
- `list_add()`
- `list_del()`
`memlayout.h` 提供 `le2page(le, member)`，可以将链表节点转换为对应的 `struct Page *`。
测试中可以检查 Buddy 的各阶空闲链表，但具体变量名和最大阶数以当前 `buddy_pmm.c` 为准。

**5. 分配与释放的行为约定**
申请 n 页时，实际分配块大小应向上取整为最小的 2 的幂。
例如：
- `n = 1`，实际分配 1 页。
- `n = 2`，实际分配 2 页。
- `n = 3`，实际分配 4 页。
- `n = 5`，实际分配 8 页。

释放时将 n 向上取整后，与块头 `property` 记录的实际块大小比较；只要取整结果相同，释放时的 n 可以与申请时不同。
例如：
``` c
struct Page *p = alloc_pages(3);
free_pages(p, 3);
```
应归还完整的 4 页块，空闲页总数增加 4。
不允许对一个已分配块进行部分释放，也不允许从分配块中间的物理页开始释放。

**6. 伙伴关系**
只有同时满足以下条件的两个块才能合并：
1. 两个块大小相同，均为 2 的幂。
2. 两个块属于同一个更高阶块的两个子块。
3. 两个块都处于空闲状态。
4. 合并后的全部页面均属于已登记的可用内存。
两个物理地址相邻的空闲块不一定能够合并。

## [GUARANTEE]
必须实现以下测试入口：
```
static void buddy_check(void);
```
确保：
```
const struct pmm_manager buddy_pmm_manager;
```
中的 `.check` 成员指向 `buddy_check`。
允许自行添加必要的 `static` 辅助函数，用于检查不同阶数的空闲链表、分配和释放、分裂与合并，以及测试结束后的状态恢复，辅助函数仅供测试内部调用，不作为新的对外接口。

## [SPECIFICATION]

### 1. buddy_check()
**Pre-Condition**
- Buddy 管理器已经初始化。
- `page_init()` 已经登记合法可用物理页。
- 各阶空闲链表和空闲页计数处于有效状态。

**Post-Condition**
- 对 Buddy 的分配、释放、分裂、合并和空闲页计数完成检查。
- 所有测试分配的物理页已经归还。
- 测试结束时空闲页总数与测试开始时相等。
- 各阶空闲链表中的空闲块大小与链表阶数一致，不存在重复登记或重叠的空闲块。

**Case 1：所有测试通过**
各项断言均成立，测试函数正常返回。

**Case 2：测试失败**
如果分配结果、块大小、伙伴关系、空闲页计数或链表状态不符合要求，应触发相应的 `assert()`，不能继续输出成功信息。

**Requirements**
测试开始时记录当前空闲页总数，结束时检查是否恢复。
可以将不同情况写入独立的测试辅助函数，由 `buddy_check()` 统一调用。

### 2. 基本物理页分配与释放检查
**Pre-Condition**
Buddy 中至少存在 3 个可分配的物理页，并且能够满足 3 次单页请求。

**Post-Condition**
- 三次单页分配均成功，分配的物理页互不相同。
- 每个分配块大小为 1 页，且不属于保留页。
- 分配后空闲页数减少 3。
- 释放后空闲页数恢复。

**Case 1：连续分配 3 个物理页**
连续调用 3 次 `alloc_page()`。
要求返回的 `p0`、`p1`、`p2` 均不为 `NULL`，并满足：
- `p0 != p1 && p0 != p2 && p1 != p2`。
- `page_ref(p0) == 0`，`page_ref(p1) == 0`，`page_ref(p2) == 0`。
- 三个页面都满足 `nbase <= page2ppn(page) < npage`。
- 三个页面均不具有 `PG_reserved` 和 `PG_property` 标志。
- 三个分配块头的 `property` 均为 1。

**Case 2：释放其中一个页面**
使用 `free_page(p1)`，要求空闲页数增加 1。
此时 `p0`、`p2` 仍为已分配状态，不能被错误地加入空闲链表。

**Case 3：再次分配一个物理页**
再次调用 `alloc_page()`，要求返回值不为 `NULL`，且不能等于仍被占用的 `p0` 或 `p2`。

**Case 4：释放全部测试页面**
释放所有尚未释放的页面，要求空闲页总数恢复到本项测试开始前。

**Requirements**
每次成功分配和释放后，空闲页计数应按实际分配块大小变化。
不能因为两个分配结果的起始地址不同，就忽略可能存在的物理页范围重叠问题。

### 3. 不同页数请求的分配检查
**Pre-Condition**
存在能够满足相应请求的空闲块。

**Post-Condition**
- 实际分配块大小是能够容纳 n 的最小 2 的幂。
- 分配块的起始物理页号按实际块大小对齐。
- 块头 `property` 保存实际分配页数。
- 空闲页总数减少实际分配块的页数，释放后恢复。

**Case 1：申请 2 页**
调用 `alloc_pages(2)`。
成功后应满足：
- `property == 2`。
- 起始物理页号能被 2 整除。
- `PageProperty(page)` 为假。
- 空闲页总数减少 2。
使用 `free_pages(page, 2)` 释放后，空闲页总数增加 2。

**Case 2：申请 3 页**
调用 `alloc_pages(3)`。
成功后应满足：
- `property == 4`。
- 起始物理页号能被 4 整除。
- `PageProperty(page)` 为假。
- 空闲页总数减少 4，而不是 3。
使用 `free_pages(page, 3)` 释放后，应归还全部 4 页。

**Case 3：申请 5 页**
调用 `alloc_pages(5)`。
成功后应满足：
- `property == 8`。
- 起始物理页号能被 8 整除。
- 空闲页总数减少 8，而不是 5。
使用 `free_pages(page, 5)` 释放后，应归还全部 8 页。

**Case 4：连续分配不同大小的块**
连续申请 1、2、3、5 页，记录每个成功分配块的起始物理页号及实际块大小。
对于任意两个块，其物理页号区间不能相交。例如申请 3 页的块应按实际占用的 4 页参与重叠检查。

**Case 5：不同 n 向上取整后块大小相同**
例如申请 5 页按 6 页释放，两次 n 向上取整后均为 8，应允许归还完整的 8 页块，空闲页总数恢复。

**Requirements**
不允许使用原始申请页数代替实际块大小计算空闲页变化和物理地址范围。
对于已经确定存在能够满足请求的空闲块的情况，如果分配返回 `NULL`，应触发断言。

### 4. 多阶空闲链表检查
**Pre-Condition**
Buddy 的各阶空闲链表已经初始化，并且管理着已登记的空闲物理页。

**Post-Condition**
各阶链表中的空闲块大小、页面标记和空闲页总数保持一致。

**Case 1：检查各阶空闲块**
遍历每个 k 对应的空闲链表。
第 k 阶链表中的每个块应满足：
- 该空闲块头具有 `PG_property` 标志。
- 头页的 `property == 2^k`。
- 起始物理页号能被 `2^k` 整除。
- 块的起始物理页号不小于 `nbase`。
- 块的结束位置不超过 `npage`。
- 块中不包含 `PG_reserved` 页面。

**Case 2：检查不同空闲块**
各阶链表中的空闲块不能互相重叠。
同一个空闲块头不能同时出现在不同 k 的空闲链表中。

**Case 3：检查空闲页总数**
统计所有 k 链表中空闲块的页数之和，要求：
```
所有空闲块的 property 之和 == nr_free_pages()
```

**Requirements**
此项检查只读取链表和页面信息，不修改分配器的内部状态。
在分裂、合并及多次分配释放之后，也应进行相同的检查。

### 5. 伙伴分裂检查
**Pre-Condition**
存在一个已确定的较高阶空闲块，且目标阶没有可直接分配的空闲块，需要从较高阶块分裂才能满足请求。

**Post-Condition**
- 较高阶块能够逐级分裂成大小相等的两个子块。
- 分配器得到符合请求大小的块。
- 未分配的子块仍保留在对应 k 的空闲链表中。
- 原父块不再作为完整空闲块存在。
- 空闲页总数只减少实际分配出去的页数。

**Case 1：从大块分裂出小块**
例如当前存在一个 16 页空闲块，目标阶没有 4 页或 8 页的空闲块，申请 4 页。
应能够通过分裂得到一个 4 页块，并保留未分配的 4 页和 8 页空闲块。

**Case 2：检查分裂后的链表**
要求：
- 原来的 16 页块不再留在对应阶数的空闲链表中。
- 新产生的 4 页和 8 页空闲块应进入各自对应的 k 链表。
- 新空闲块的 `property` 和 `PG_property` 标志正确。
- 已分配的 4 页块不能同时出现在空闲链表中。
- 分裂后的全部块互不重叠，页数之和没有变化，除去本次分配的 4 页后，其余页面仍为空闲。

**Case 3：再次分配**
在上述分裂后的受控内存区域中继续申请小块，应能够使用未分配的部分。
**Requirements**
必须确认本次分配确实使用了较高阶空闲块，不能仅因为 `alloc_pages(4)` 成功就认为已经检查了分裂。
可以通过比较分裂前后的各阶空闲块状态来判断。

### 6. 伙伴合并检查
**Pre-Condition**
存在两个大小相同、属于同一个父块的合法伙伴块，能够分别对它们进行分配和释放。

**Post-Condition**
- 只有两个伙伴都空闲时才能合并。
- 合并后的块大小为原来块大小的两倍。
- 被合并的子块不再单独保留在低阶空闲链表中。
- 如果合并后的块仍有合法的空闲伙伴，应能够继续向上合并。

**Case 1：只有一个伙伴空闲**
例如两个 4 页块构成一个 8 页父块。
当其中一个 4 页块仍被占用时，释放另一个 4 页块，不能形成一个完整的 8 页空闲块。

**Case 2：两个伙伴均被释放**
释放另一个 4 页块后，应能够合并为一个 8 页空闲块。
要求：
- 合并后的块大小为 8 页。
- 合并块头的 `property == 8`。
- 起始物理页号能被 8 整除。
- 原来的两个 4 页块不再作为两个独立块出现在低阶链表中。
- 空闲页数只按实际释放的页数增加，合并操作本身不增加空闲页数。

**Case 3：递归合并**
如果新形成的 8 页空闲块还有一个大小为 8 页的空闲伙伴，应继续合并为 16 页块。
检查合并后的块大小、头页标志及对应 k 链表，直到无法继续合并或达到最大 k。

**Case 4：两个块不是合法伙伴**
对于大小不同，或者虽然大小相同但不属于同一个父块的相邻空闲块，不能进行合并。
不能形成大小不是 2 的幂的空闲块，也不能把未登记页面或保留页合并进来。
特别检查两个同阶空闲块虽物理地址相邻、但属于不同父块时，不能错误合并。

**Requirements**
必须检查实际合并后的块及各阶链表状态，不能只通过空闲页总数恢复判断伙伴合并正确。

### 7. 分配失败检查
**Pre-Condition**
Buddy 已经初始化，当前空闲页数量能够通过 `nr_free_pages()` 获取。

**Post-Condition**
当不存在能够满足请求的空闲块时返回 `NULL`，空闲页总数及各阶空闲链表状态不变。

**Case 1：申请页数超过空闲页总数**
记录当前空闲页数 `nr_free`。
申请超过 `nr_free` 的页数，要求分配失败并返回 `NULL`。
分配前后的 `nr_free_pages()` 应相等。

**Case 2：总空闲页数足够但没有满足请求的块**
例如当前只有若干个相互分离的 2 页空闲块，空闲页总数不少于 4，但没有 4 页或更高阶的空闲块。
此时申请 4 页应返回 `NULL`。

**Case 3：检查失败后的状态**
分配失败后，各阶链表中的空闲块数量、块头地址、`property` 和空闲页总数应保持不变。
已经分配出去的块不能因为本次分配失败而重新进入空闲链表。

**Requirements**
对于第二种情况，需要先确认测试状态中确实不存在可分裂得到目标块的更高阶空闲块。
不得直接破坏真实内核空闲链表来构造测试场景。
对于 `n == 0`、重复释放、错误起始地址等会触发断言的非法调用，不应放入正常启动时必须成功返回的 `buddy_check()` 中。

### 8. 多次分配释放及最终状态检查
**Pre-Condition**
Buddy 中存在可用于测试的空闲物理页，且各阶链表状态正确。

**Post-Condition**
- 所有测试中分配的页面均已释放。
- 空闲页总数恢复到测试开始前。
- 各阶链表中的空闲块没有丢失、重复登记或重叠。
- 没有已分配页面仍被错误地计为空闲页。

**Case 1：不同顺序释放**
连续分配不同大小的块后，不按照分配顺序释放，而是交错释放。
每次释放后检查 `nr_free_pages()` 增加的数量是否等于对应块的实际大小。
尚未释放的块不能被错误地加入空闲链表。

**Case 2：重复分配和释放**
重复进行若干轮不同大小的分配、释放操作。
每一轮全部释放后，空闲页数应恢复到该轮开始前。

**Case 3：最终空闲页数检查**
记录 `buddy_check()` 开始时的空闲页数 `free_before`。
检查全部完成后，应满足：
```
nr_free_pages() == free_before
```

**Case 4：最终空闲链表检查**
再次遍历各阶链表，检查：
- 第 k 阶空闲块的大小仍为 `2^k`。
- 每个空闲块头的 `PG_property` 和 `property` 正确。
- 空闲块之间不重叠。
- 各阶空闲块的页数之和等于 `nr_free_pages()`。

**Requirements**
所有测试过程中分配的页面都必须归还。
如果为了测试分裂、合并或分配失败而临时修改了 Buddy 的测试状态，应在返回前完整恢复原有的空闲链表、空闲页计数和必要的 Page 信息。
不能只恢复空闲页数量，却留下错误的链表节点或页面状态。


### 9. `buddy_init_memmap()` 登记检查
**Pre-Condition**
- Buddy 已初始化；待登记页面具有 `PG_reserved` 标志，且尚未加入空闲链表。
- 测试不能破坏当前正在使用的物理页。

**Post-Condition**
输入区间内的 n 页全部登记，空闲块按自身大小对齐且互不重叠，空闲页总数增加 n，未登记区域不被加入空闲链表。

**Case 1：区间长度不是 2 的幂，起点未按大块对齐**
例如在 16 页对齐区域中登记偏移 4 页、长度 12 页的区间，应保留一个 4 页块和一个 8 页块，共登记 12 页，不包含前面未登记的 4 页。

**Case 2：多次登记相邻区间**
分次登记的相邻空闲块在满足同阶伙伴条件时应能够合并。检查空闲页数累计正确，合法伙伴最终可以合并成更高阶块。

**Case 3：多次登记不相邻区间**
例如分别登记偏移 0 和偏移 8 处各 4 页，中间 4 页未登记。应保留两个独立的 4 页块，不得跨越未登记区间合并；只有这些空闲页时，申请 8 页应返回 `NULL`。

**Requirements**
检查页面标志、块大小、对齐、各阶空闲链表和空闲页计数。测试结束后恢复原有管理状态，不得重复登记真实空闲页。

### 10. 非法释放检查
**Pre-Condition**
测试对象为已经成功分配且尚未释放的物理页块，已知其实际大小和起始页号。

**Post-Condition**
释放起始位置未对齐，或者 n 向上取整后与块头 `property` 不一致时，应触发相应断言，拒绝非法释放。

**Case 1：n 向上取整后小于实际块大小**
对实际大小为 4 页的分配块以 n = 2 释放，应触发块大小不匹配的断言。

**Case 2：n 向上取整后大于实际块大小**
对实际大小为 4 页且起始页号满足 8 页对齐的分配块以 n = 5 释放，应触发块大小不匹配的断言，而不是对齐断言。

**Case 3：释放起始页号未对齐**
对实际大小为 4 页的分配块，从起始页之后一页开始以 n = 4 释放，应触发起始页号未对齐的断言。

**Requirements**
三个 Case 分别进行预期触发断言的测试，默认不在正常 `buddy_check()` 中执行。应确认触发的是对应断言，不能把任意 panic 当作测试通过。不得修改 `buddy_free_pages()` 的原有逻辑。
````

#### 实现迭代过程

本模块的实现经历了 4 次迭代，过程如下：

---

##### 第一次迭代

**遇到的问题：**
- 普通分配和释放虽然可以通过断言检查返回值与空闲页数，但 Buddy 的分裂、合并需要确定具体空闲块的大小和位置，不能直接假设真实内存中的分配地址固定。
- 在分裂测试中，曾把一个 4 页块再次分裂后剩余的 2 页块误认为第 2 阶，实际上 2 页对应第 1 阶，导致断言失败；这是测试预期错误，不是分配器分裂错误。

**问题解决策略：**
- 在第二份提示词的 `[SPECIFICATION]` 中补充各阶链表和页面状态检查；对需要固定布局的情况，要求使用从真实分配器申请的 16 页对齐受控区域，并在测试结束时恢复真实链表和空闲页计数。
- 在 `[RELY]` 中明确第 k 阶对应 `2^k` 页，并要求 AI 修正分裂后错误的阶数断言，同时检查剩余块地址、头页 `property`、`PG_property` 及空闲页数变化。

**最终结果：**
- 实现 `buddy_check()` 及基本分配、不同页数请求、多轮分配释放、空闲链表、分裂、合并和分配失败等测试函数。
- 修正测试断言后，编程 AI 报告 `make` 编译通过，QEMU 输出 `check_alloc_page() succeeded!`，测试正常返回。

**关键改进点总结：**

1. 不能只检查 `alloc_pages()` 是否返回非 `NULL`，还需要检查实际块大小、地址对齐、页面标志和各阶链表。
2. 在真实内存中不能假设固定返回地址；只有先确定测试区域的空闲块布局，才能检查分裂和合并后的具体位置。

##### 第二次迭代

**遇到的问题：**
- 初版测试使用原始申请页数释放，没有覆盖申请 n 和释放 n 不同、但向上取整后的块大小相同的合法情况。
- 原有不合并测试涉及不相邻的同阶块和相邻的不同阶块，没有直接检查两个物理地址相邻、大小相同但不是真正伙伴的块是否会被错误合并。

**问题解决策略：**
- 在补充提示词中要求 AI 修改 `buddy_sizes_check()`，增加同一取整区间的释放测试，如申请 3 页按 4 页释放、申请 5 页按 6、7、8 页释放，并检查 `property` 和空闲页数是否按实际块大小处理。
- 在补充提示词中要求 AI 修改 `buddy_no_merge_check()`，增加 16 页受控区域的四个 4 页块场景，先释放中间两个相邻但不属于同一父块的块，要求它们保持独立；随后释放合法伙伴，再检查能否逐级合并。

**最终结果：**
- 增加的两类测试均通过。合法的不同 n 释放能够归还完整块，空闲页数恢复；相邻但不是伙伴的两个 4 页块没有错误合并。
- 编程 AI 报告 `make` 编译通过，QEMU 继续输出 `check_alloc_page() succeeded!`，分配与释放算法代码未修改。

**关键改进点总结：**

1. `buddy_free_pages()` 检查的是 n 向上取整后的大小与块头 `property` 是否相等，不是原始 n 是否完全相同。
2. 两个空闲块即使同阶且物理地址相邻，也必须属于同一个父块才能合并。

##### 第三次迭代

**遇到的问题：**
- 前两轮测试主要检查分配、释放及伙伴操作，没有直接测试 `buddy_init_memmap()` 对非 2 的幂长度和非高阶对齐区间的处理。
- 多次登记相邻或不相邻区间时，既要检查合法伙伴能否合并，也要防止跨越未登记页面错误合并；直接使用真实空闲链表重新登记会破坏现有管理状态。

**问题解决策略：**
- 在 `[SPECIFICATION]` 中增加 `buddy_init_memmap()` 检查要求，说明要复用已有的 16 页受控区域，并按照 `buddy_init_memmap()` 的前置条件准备带有 `PG_reserved` 标志且未登记的页面。
- 在提示词中明确三个 Case：长度为 12 页、起点偏移 4 页的区间；分次登记可合并成 16 页的相邻区间；中间保留 4 页的不相邻区间。要求分别检查块大小、对应阶数、空闲页数和保留页状态。

**最终结果：**
- 新增 `buddy_init_memmap_check()` 并接入受控测试流程。12 页区间按对齐要求划分为 4 页和 8 页块；多次相邻登记最终合并为 16 页块；不相邻的两个 4 页块没有跨越未登记区间合并，申请 8 页返回 `NULL`。
- 编程 AI 报告编译通过，QEMU 中 `check_alloc_page() succeeded!` 正常输出。

**关键改进点总结：**

1. `init_memmap()` 必须登记输入范围内的全部物理页，但每个空闲块仍须为 2 的幂大小并按自身大小对齐。
2. 通过分次登记和保留页检查，可以验证合并既不会遗漏合法伙伴，也不会越过未登记区间。

##### 第四次迭代

**遇到的问题：**
- 正常执行的 `buddy_check()` 无法直接检验非法释放是否被拒绝，因为预期触发的断言会使内核停止运行。
- 测试释放页数向上取整后大于实际块大小时，如果起始位置不满足较大块的对齐条件，会先触发对齐断言，不能证明块大小比较本身正确。

**问题解决策略：**
- 在补充提示词中要求增加默认关闭的 `BUDDY_ILLEGAL_FREE_TEST`，用 1、2、3 分别选择“释放大小过小”“释放大小过大”“起始页号未对齐”三种负向测试，正常模式保持为 0。
- 在提示词中明确三种负向测试的输入条件：在 16 页对齐受控区域申请实际大小为 4 页的块，分别使用 `free_pages(page, 2)`、`free_pages(page, 5)` 和 `free_pages(page + 1, 4)`；前两种情况必须先满足起始地址对齐要求，第三种情况专门检查起始页号未对齐。

**最终结果：**
- 编程 AI 分别运行三个模式：模式 1、2 均在 `assert(base->property == (unsigned int)size)` 处按预期 panic；模式 3 在 `assert((index & (size - 1)) == 0)` 处按预期 panic。
- 恢复默认模式后，`make` 编译通过，QEMU 输出 `check_alloc_page() succeeded!`。三种 panic 是预期非法输入检查结果，不属于正常测试失败。

**关键改进点总结：**

1. 预期触发断言的非法输入测试应分别启用，并检查具体失败的断言，不能把任意 panic 当作测试通过。
2. 大小不匹配与起始页号未对齐需要分别构造输入，保证每项测试验证的是对应的释放条件。

**3. 为什么这些测试能够有效检验 Buddy System 实现**

Buddy 分配器的核心不只是返回一段可用物理页，而是要保证**块大小为 2 的幂、按块大小对齐、正确分裂和合并、各阶链表与空闲页数一致**。因此，测试同时检查分配和释放的返回结果，以及操作前后各阶链表中具体有哪些空闲块。即使空闲页总数正确，只要出现块放错阶、重复登记、错误合并或分裂剩余块丢失，也会被相应断言检查出来。

分裂、合并和分配失败测试使用可恢复的 16 页对齐受控区域，能够确定测试前的空闲块位置和阶数，所以可以对预期的分裂结果、伙伴位置和合并后的块大小作出具体检查，而不依赖真实内存中不确定的分配地址。三种非法释放情况则分别启用 `BUDDY_ILLEGAL_FREE_TEST=1/2/3`，核对触发的是对应的块大小或对齐断言；由于内核会按预期停止，这些负向测试不放在正常模式下连续执行。最后检查测试前后空闲页数及链表状态是否恢复，防止测试本身影响内核后续的内存管理。

## 六、实验总结与收获

### 对操作系统的理解

1. **物理页管理与内存分配策略。** ucore 用 `Page` 数组表示物理页，用 `pmm_manager` 统一管理初始化、分配、释放和检查。Buddy 是其中一种物理页分配策略，通过多阶空闲链表把连续空闲页组成 2 的幂大小的块。与单纯维护连续空闲区间不同，Buddy 的分裂和合并受到阶数与伙伴关系约束。
2. **内存碎片。** Buddy 通过分裂与合并减少可用块的管理难度，但请求 n 页时需要向上取整，例如申请 5 页占用 8 页，可能产生内存碎片。总空闲页数足够也不一定存在一个满足连续页请求的空闲块。
3. **页面状态与地址范围。** `PG_reserved` 区分不可分配页面，`PG_property` 标记空闲块头；已分配块头保留实际大小以便释放检查。页号需要按实际块大小对齐，分配和合并也不能越过已登记的可用物理内存范围。
4. **本实验没有直接涉及的内容。** 虚拟地址空间、页表权限、TLB、页面置换及交换空间同样属于操作系统内存管理的重要内容，但它们不属于本次 Buddy 物理页分配任务的直接实现范围。

### AI 协作开发的经验

这次任务分成两份提示词：第一份只要求 AI 生成 Buddy 算法并接入内核，第二份只要求编写测试函数，不允许为了通过测试去修改算法。这样可以把算法实现和正确性检查分开，避免在调试测试时无意改变原有分配行为。

编写提示词时，使用 `[PROMPT]` 明确任务与修改范围，在 `[RELY]` 中给出必要的内核接口，在 `[GUARANTEE]` 中限定函数签名，在 `[SPECIFICATION]` 中用 Pre-Condition、Post-Condition 和 Case 描述可检验条件。相比只要求“保证地址合法”或“正确合并”，明确 `property == 2^k`、`nr_free_pages()` 的变化、物理页范围和伙伴关系，更容易检查 AI 生成的实现是否符合要求。
