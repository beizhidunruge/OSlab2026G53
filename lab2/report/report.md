## 三、实验整体逻辑分析

### 3.1 本章节的逻辑主线

主线是“发现 RAM → 保护已占用区域 → 登记可用物理页 → 按策略分配和回收 → 验证地址与状态”。启动汇编预置页表并打开 Sv39 后，C 代码才能以高虚拟地址操作内核数据。`dtb_init()` 获取 RAM 起点和长度，`page_init()` 将它们转化为 `Page` 描述符布局与可用区间，再经 `pmm_manager` 交给具体分配策略。

```text
entry.S：配置启动根页表，开启 Sv39 并转入高地址
  → kern_init / dtb_init：初始化并读取 RAM 信息
  → pmm_init / init_pmm_manager：选择分配器并清空其内部状态
  → page_init：建立 Page 数组，保留固件、内核、元数据及对齐占用
  → init_memmap：登记完整空闲页
  → 当前管理器的 check：内部调用 alloc_pages / free_pages 检查状态和算法行为
  → 后续公开分配/释放：选择、分裂、回收、合并
```

页表负责虚拟地址到物理地址的转换，`Page` 数组负责物理页状态；二者都占 RAM，但用途不同。连续物理页分配也不等于进程虚拟地址空间管理。

### 3.2 功能的逐步实现

先用已有 First-Fit 验证初始化，再实现 Best-Fit 并切换运行，避免把错误内存布局与错误选择算法混在一起。Buddy 使用相同接口，但采用二次幂容量和整块释放约定，因此使用自己的检查函数独立验证，不能把 Best-Fit 的部分释放测试直接套给它。MMU 分支则在真实访存上观察地址翻译，补足只看分配代码无法展示的硬件过程。

## 四、实验内容与实现

### 功能模块一：物理内存探测与页描述符初始化

**负责人：** 2414034-丁欣怡

#### 模块功能与核心函数

```c
static void page_init(void);  // kern/mm/pmm.c
```

`page_init()` 根据设备树给出的 RAM 范围建立物理页管理元数据，保护固件、内核和元数据占用，再将可用的完整页交给当前分配器。调用链为 `kern_init → dtb_init → pmm_init → init_pmm_manager → page_init → init_memmap`。启动汇编已经建立页表并开启 Sv39，本函数不重新创建页表。

这里需要区分三个对象：物理页是 4 KiB 内存，`struct Page` 是记录物理页状态的描述符，PTE 是供 MMU 翻译地址的页表项。描述符和页表本身都占 RAM，但页表决定地址映射，描述符记录物理页归属，不能相互替代。

#### 规格设计与实现说明

规格先明确地址含义，再规定检查和状态转换：

1. 通过 `get_memory_base()`、`get_memory_size()` 获取 RAM。零长度、起点不等于框架的 `DRAM_BASE`、`base + size` 溢出均终止初始化。固定起点来自启动映射和 `nbase` 的约束，不能只替换一个起点变量就声称支持任意布局。
2. 将 `va_pa_offset` 设为 `PHYSICAL_MEMORY_OFFSET`，即 `0xffffffff40000000`。DTB 末端还要受 `PHYSICAL_MEMORY_END` 和 `KERNTOP` 对应物理上界约束，取最小值并向下按页对齐，得到 `maxpa`。
3. 设置 `npage = maxpa / PGSIZE`。`npage` 是绝对物理页号上界，描述符数量为 `npage - nbase`，不是 `npage` 个。
4. 将链接符号 `end` 向上按页对齐，作为 `pages` 的虚拟起点；转换为物理地址后，检查内核和整个描述符数组都能放入管理区间，再写入描述符。使用减法、除法检查容量，避免乘加运算先溢出再判断。
5. 全部描述符先设置 reserved，引用计数和块长清零，链表节点初始化。描述符数组末尾向上按页对齐得到 `freemem`，仅在 `freemem < maxpa` 时登记空闲页。

核心关系可写为：

```c
npage = maxpa / PGSIZE;
// pages 位于 end 之后，描述符覆盖 [nbase, npage)。
// freemem 是描述符数组末尾向上按页对齐后的物理地址。
if (freemem < maxpa) {
    init_memmap(pa2page(freemem), (maxpa - freemem) / PGSIZE);
}
```

先全部保留、再开放可用区，能避免固件、内核、描述符和对齐空隙被提前分配。`init_memmap()` 通过当前管理器的回调登记页面，因此这一初始化可供不同分配策略复用。

地址转换也构成函数的契约：`pages` 是可供内核访问的虚拟地址，传给 `pa2page()` 的必须是物理地址，不能混用。描述符数组的物理起点由 `PADDR(pages)` 得到，其容量检查等价于“描述符个数不超过剩余物理字节数除以结构体大小”。保留数组占用后，实际能分配的页数小于设备树报告的总页数；元数据自举本身也消耗内存。初始化同时输出设备树区间、管理区间和可用区，使集成阶段能够分别核对裁剪和保留是否正确。

### 功能模块二·任务一：理解 First-Fit 连续物理内存分配

**负责人：** 2412591-贺翰林

#### 模块功能描述与核心函数

本项阅读框架已有实现，不重新生成或修改 First-Fit。相关函数为：

```c
static void default_init(void);
static void default_init_memmap(struct Page *base, size_t n);
static struct Page *default_alloc_pages(size_t n);
static void default_free_pages(struct Page *base, size_t n);
static size_t default_nr_free_pages(void);
```

`free_area_t` 保存按地址递增的空闲块链表及空闲页总数。链表只挂空闲块首页，首页 `PG_property` 标志说明块长有效，`property` 保存连续页数。非首页也可能属于空闲块，所以不能把未设置首页标志等同于已分配。

`default_init()` 建立空循环双向链表并清零计数。`default_init_memmap()` 将上层传入的连续保留页转换为可分配页，重置状态和引用计数，设置首页及长度，增加计数并按地址插入。

`default_alloc_pages(n)` 从头查找，遇到第一个长度不小于 `n` 的块立即停止；摘除后分配前 `n` 页，余下区间以新的首页放回原位置，空闲数减少 `n`。若总量足够但没有足够连续的单块，也会返回 `NULL`。返回的是描述符，不是直接可访问的页内容，且不负责清空物理页数据。

`default_free_pages()` 逐页重置状态，将释放区间有序插回。前驱满足 `p + p->property == base` 才能向前合并，随后以新的块首检查后继。链表相邻不代表物理相邻；合并只是组织变化，不再次增加页数。当前 `default_init_memmap()` 只登记排序，没有额外合并步骤。

#### 原有 First-Fit 是否有进一步改进空间

有。空闲块数为 `k` 时，分配和释放定位最坏均需 O(k) 搜索。可用按地址索引并维护子树最大块长等结构加快“第一个可满足块”的定位，但会增加维护成本。若改为按大小选择，则已改变 First-Fit 的规则。

当前已经合并相邻空闲块，不能将其写成尚未实现的优化。Next-Fit、Best-Fit 等可作策略对照，但不保证普遍减少碎片；仍被占用的页面会阻断合并。该阅读任务无代码生成 prompt，AI 辅助用于理解函数和状态转换，不补造生成记录。

### 功能模块二·任务二：实现 Best-Fit 连续物理内存分配

**负责人：** 2412591－贺翰林

#### 模块功能描述与需要实现的接口

```c
static void best_fit_init(void);
static void best_fit_init_memmap(struct Page *base, size_t n);
static struct Page *best_fit_alloc_pages(size_t n);
static void best_fit_free_pages(struct Page *base, size_t n);
static size_t best_fit_nr_free_pages(void);
static void best_fit_insert_free_block(struct Page *base);
const struct pmm_manager best_fit_pmm_manager;
```

规格从 `pmm_manager` 的回调职责和两个现有测试形成：初始化后链表为空，登记仅开放有效页，成功分配恰好 `n` 个连续页且减少相应计数，失败保持状态，释放后完成可能的相邻合并，查询不改变状态。分配又区分总量不足、无连续候选、精确匹配和分裂；释放区分无邻居、单侧和双侧相邻。

内部保留静态 `free_area_t`，提供测试直接读写的 `free_list`、`nr_free`。链表按地址组织，分配按大小选择所有可用块中的最小者；同长时保留地址最低者，精确匹配可提前结束。关键判断为：

```c
if (p->property >= n &&
    (page == NULL || p->property < page->property)) {
    page = p;
    if (p->property == n) {
        break;
    }
}
```

例如按地址存在 2、7、4 页三个块，申请 3 页时 First-Fit 取 7 页块，Best-Fit 取 4 页块。选中块被摘除，余下部分从 `page + n` 开始重新登记；分出去的首页清除标志和旧块长。初始化登记和释放共同调用 `best_fit_insert_free_block()`，按地址插入、前后合并，计数由调用者只更新一次。

测试会暂时清空链表却尚未清零计数，所以分配仍要依据实际遍历结果返回 `NULL`。测试还允许对分别取得的连续已分配区间一次释放，因此本模块不增加必须匹配单次分配记录的约束。注册结构的 `.check` 绑定原有 `best_fit_check()`，其内部调用 `basic_check()`；两个函数保持不变。

````markdown
## best_fit_init_memmap

**Pre-Condition**：`n > 0`；`[base, base + n)` 对应有效、连续、尚未登记的物理页，当前均处于保留状态；管理器已初始化。

**Post-Condition**：该范围变为可管理空闲页，引用计数重置为 0，清除保留状态，正确设置块首页标记及长度；地址顺序保持正确，空闲页总数恰增加 `n`。

**Case 1**：链表为空时，登记为首个空闲块。

**Case 2**：链表非空时，在正确地址位置登记，不丢失已有块、不产生重叠。若对相邻登记区间进行合并，须同步更新首页标记和长度；登记不跨越保留页或不可用区间。

**Requirements**：对 `n > 0` 和登记页的保留状态采用与参考实现一致的断言检查。

## best_fit_alloc_pages

**Pre-Condition**：`n > 0`，空闲块元数据有效；允许现有测试临时清空链表而尚未同步计数。

**Post-Condition**：成功则返回连续、恰好 `n` 页的首页描述符，分配区间不再属于空闲链表且其中没有空闲块首页标记，`nr_free` 恰减少 `n`；失败则返回 `NULL`，链表、页状态和计数均不变。

**Case 1**：空闲总页数不足，或链表为空，或虽总页数足够但所有单块长度均小于 `n`，返回 `NULL`。

**Case 2**：存在可用块时，选择所有长度不小于 `n` 的块中最小者。若多个块同样最小，本设计选择地址最低者。精确匹配已经达到最优，可提前结束搜索；不能遇到任意足够大的块就停止。

**Case 3**：最优块长度等于 `n`，整块分配，从空闲链表移除并更新状态和计数。

**Case 4**：最优块长度大于 `n`，分配该块前部 `n` 页，余下连续区间继续作为空闲块，正确设置新的首页标记和长度，并保持地址有序。

**Requirements**：断言 `n > 0`；返回区域引用计数符合现有测试的零值约定；不能因空闲总页数足够就返回不连续页面，不能返回超出请求页数的整个大块。

## best_fit_free_pages

**Pre-Condition**：`n > 0`；`[base, base + n)` 是有效、连续、已分配且允许释放的页，不包含保留页，也不与已有空闲块重叠。允许一次释放由多次分配得到的连续区间；调用者负责保证范围有效。

**Post-Condition**：整个范围回到空闲管理状态，释放页的引用计数重置为 0，`nr_free` 恰增加 `n`；最终空闲块不重叠，首页标记和长度正确，地址顺序保持不变，所有可与本次释放区间相接的空闲块完成合并。

**Case 1**：链表为空，或左右均无物理相邻块，将释放范围登记为独立空闲块。

**Case 2**：仅前方或仅后方有物理相邻块，合并为一个连续块，保留合并后最低地址页作为首页，移除失效首页的链表节点和标记。

**Case 3**：前后均有物理相邻块，最终合并为一个完整大块，不因第一次合并改变首页而漏掉另一侧。

**Requirements**：使用与参考实现一致的 `n > 0`、非保留页及非空闲块首页断言；不宣称这些断言能够检测全部非法释放。合并只调整组织结构，不重复增加空闲页计数。

**Pre-Condition**：管理器已初始化。

**Post-Condition**：返回当前 `nr_free`，不改变任何状态。
````

有。当前分配最坏 O(k)，登记和释放为 O(n+k)，其中 `k` 是空闲块数、`n` 是逐页处理的范围。可用按 `(块长, 地址)` 索引寻找最小可满足块，同时维护地址关系以合并，但要同步分裂、合并和测试恢复所需状态。当前操作辅助空间为 O(1)，全局描述符存储仍随物理页数增长。

#### 模块功能与函数接口

Buddy 把连续物理页组织成 `2^k` 页的块，分配时逐级分裂，释放时合并同阶伙伴，通过既有 `pmm_manager` 接口接入内核。

```c
static void buddy_init(void);
static void buddy_init_memmap(struct Page *base, size_t n);
static struct Page *buddy_alloc_pages(size_t n);
static void buddy_free_pages(struct Page *base, size_t n);
static size_t buddy_nr_free_pages(void);
static void buddy_check(void);
extern const struct pmm_manager buddy_pmm_manager;
```

`buddy_free_area[k]` 是第 k 阶空闲链表，节点代表一个 `2^k` 页的块；该阶 `nr_free` 记录页数，`buddy_nr_free` 记录全部空闲页数。空闲块头设置 `PG_property`，`property` 保存实际容量；已分配块头清除该标志，但仍保留实际容量，内部页的 `property` 为 0。

`buddy_init()` 初始化各阶链表和计数；`buddy_init_memmap()` 按 `base - pages` 的全局下标，把输入区间完整拆成自然对齐的二次幂块，并尝试与此前登记的伙伴合并。`buddy_alloc_pages(n)` 取能够容纳 n 的最小二次幂，寻找最小可用阶，必要时分裂并保存剩余半块。申请 3 页实际占用 4 页，申请 5 页实际占用 8 页，空闲计数按实际容量扣减，内部余量不能另行分配。

`buddy_free_pages(base,n)` 要求 base 是完整分配块的首页，且 n 向上取整后等于块头记录的实际容量。它允许申请 5 页后按 6、7 或 8 页归还同一个 8 页块，拒绝从块内部开始或只归还部分页面。伙伴下标为 `index ^ size`，只有伙伴在管理范围内、已经登记、不是保留页、为空闲块头且容量相同时才合并；合并后继续检查上一阶。物理相邻且大小相同仍不一定属于同一父块，因此不能直接合并。

````markdown
- `page2pa(page)`：转换为物理地址；
- `pa2page(pa)`：将物理地址转换为描述符。

当前代码的映射关系为：

``` c
page2ppn(page) = page - pages + nbase
```

因此，`pages[0]`对应物理页号`nbase = 0x80000`，可以使用在pages数组中的位置即数组下标来代替物理页号的使用。

**5. Buddy System 的伙伴关系**

伙伴块必须同时满足：
1. 两个块大小相同，均为 2 的整数次幂。
2. 两个块是同一个更高阶块分裂产生的左右子块。
3. 两个块都处于空闲状态。
4. 合并后的整个范围都属于已注册且可管理的物理页面。

对于大小为 `2^k` 页的块，其起始物理页号必须是 `2^k` 的整数倍，当满足该对齐条件时，其伙伴起始页号可以通过起始页号与 `2^k` 异或得到。但计算出的地址还必须经过范围和状态检查。

## [SPECIFICATION]

### 1. buddy_init()
**Pre-Condition**
- 内核已经选择 Buddy 作为管理器。
- 此时尚未通过 Buddy 登记可用物理页。

**Post-Condition**
- 所有k对应的空闲链表初始化完毕，处于空状态。
- 当前空闲页计数置为 0。

**Case 1：正常初始化**
初始化所需的空闲链表和统计状态，供 `init_memmap()` 注册可用页面。

**Requirements**
根据可用物理内存上限来确定最大k。
此函数只初始化 Buddy 的管理状态。

### 2. buddy_init_memmap(struct Page *base, size_t n)
**Pre-Condition**
- Buddy 内部状态已经初始化。
- `base` 指向一个此前未注册的、连续可用的物理页描述符区间`base`，`[base, base + n)` 代表已经由上层确认可用、尚未登记的连续物理页。
- `n > 0`。
- 输入范围不包括内核镜像、OpenSBI、页描述符数组或其他保留区域。

**Post-Condition**
- 全部 `n` 个物理页被登记为空闲页。
- 该区间被变为一个或多个互不重叠、大小为 2 的幂、按自身大小对齐的空闲块。
- 所有被登记的页`flag`除`PG_property`为0，引用计数为 0。
- 每个空闲块头页具有正确的 `PG_property` 状态及 `property` 值。
- 每个空闲块进入其对应 k 的空闲管理结构。
- 空闲页总数增加 `n`，登记过程中不会丢失页面或重复统计页面。

**Case 1：输入只有一个物理页**
当 `n = 1` 时，应登记一个 k = 0 的空闲块，空闲页数增加 1。

**Case 2：区间长度不是 2 的幂**
必须能够将区间划分为多个 2 的幂大小的合法块，而不是丢弃多余页面。
例如输入包含 13 个连续页。不得丢弃多余页面，应拆为若干合法的二次幂块，最终登记页数之和必须为 13。

**Case 3：传入起始位置未按大块对齐**
必须根据物理页号处理对齐。
例如可用区间的物理页号范围为 `[3,16)` 时，可形成大小为 1、4、8 页的合法块，分别为 `[3,4)`、`[4,8)`、`[8,16)`。

**Case 4：多次登记可用区间**
多次调用可登记不同的、不重叠的可用物理页区间。新的登记不能破坏已存在的空闲块。
对于物理位置相邻、大小相同且满足 Buddy 关系的完整空闲块，允许并应能够最终合并。不能越过保留页或未登记区间合并。

**Case 5: 非法输入**
- `n <= 0`
- 有页不为保留页

**Requirements**
- 不允许注册输入区间以外的页。
- 对重叠或重复登记的非法输入应进行检查，不能把同一页重复加入空闲链表。
- 必须使用 base - pages 取得全局下标，而不能把每次登记区间的起点当作新的下标 0

### 3. buddy_alloc_pages(size_t n)

**Pre-Condition**
- Buddy 已完成初始化及必要的物理页登记。
- `n > 0`。
- 各阶空闲管理结构保持一致。

**Post-Condition**
成功时：
- 返回一个有效的 `struct Page *`，指向实际分配块的起始页。
- 返回块包含至少 `n` 个连续物理页，实际块大小是能够容纳 `n` 的最小合法二次幂， `property`为实际块大小，不记录实际申请的块大小，按自身大小对齐。
- 被分配的块不再作为空闲块留在任何k链表中。
- 空闲页总数减少实际分配块的页数，返回块中的首页应从空闲状态转为已分配状态。

失败时返回 `NULL`，且原分配器状态保持不变。

**Case 1：n为非 2 的幂**
应向上取整为能够容纳请求的最小 2 的幂页数。例如 `n=3` 实际保留 4 页，`n=5` 实际保留 8 页。多出的页面属于当前分配块，不能再拆分分配。空闲页计数应按照实际分配块的容量减少。

**Case 2：存在恰好匹配的空闲块**
例如请求 4 页且存在可用的 4 页伙伴块时，可以直接分配该块。
维护头页标记、分配信息及空闲页计数。

**Case 3：只有更大的空闲块**
- 寻找能够满足请求的更高阶且阶数最小的空闲块，并逐级对半拆分，每次拆分后两个子块大小相等，均为父块的一半；
- 未分配出去的伙伴子块继续保持可用，应纳入相应 k 的空闲管理结构，已被拆分的父块不得继续作为一个完整空闲块出现。例如存在 16 页块而申请 4 页时，应能够保留未分配的 12 页供后续使用，但是已经被拆分成4，8。
- 维护头页标记、分配信息及空闲页计数。

**Case 4：没有可满足请求的连续 Buddy 块**
当不存在足够大小的合法空闲块时返回 `NULL`。
这不仅包括总空闲页数不足，也包括虽然总空闲页数足够，但不存在满足请求大小的连续且可合并空闲块。
失败后空闲块结构、页面状态和空闲页统计必须保持不变。

**Case 5：异常参数**

- `n == 0`：使用 `assert` 拒绝非法调用。
- 当 `n` 过大，无法安全地计算向上取整后的 2 的幂大小或者超过 Buddy 所支持的最大块容量时，应返回 `NULL`

**Requirements**
成功返回块的起始物理页号必须满足实际块容量的对齐要求。
每个成功分配的块只有空闲块大小，不记录实际申请的页数。

### 4. buddy_free_pages(struct Page *base, size_t n)

**Pre-Condition**
- `base` 是此前一次成功分配的起始页，对应的分配块尚未被释放。
- `n > 0`，为该次分配的原始请求页数。
- 调用的请求n向上取 2 的幂后，必须与该块记录的实际分配大小一致。
- 不允许从块内部任意位置开始释放，也不允许对为空闲块重复释放。

**Post-Condition**
- 整个原始分配块变为空闲块。
- 若同阶伙伴块空闲，则能够逐级合并。被合并的两个子块不再作为独立块存在，起始物理页号满足对齐要求。
- 维护头页标记、分配信息及空闲页计数，空闲页只增加本次归还的实际页数。

**Case 1：伙伴不存在、未登记或不空闲**
只释放当前块，不进行合并。

**Case 2：两个同阶伙伴均为空闲**
两个块应合并为一个大小翻倍的空闲块。
若合并后的块仍有符合条件的空闲伙伴，应继续向上合并。直到遇到不可合并的伙伴、管理范围边界或最大k。

**Case 3：相邻块并非同阶伙伴**
即使它们物理连续，也不能错误合并。

**Case 4：非 2 的幂请求释放**
n向上取 2 的最小幂。例如 `alloc_pages(3)` 实际占用 4 页，应允许使用 `free_pages(base, 3)` 释放 4 页。

不能只归还 3 页，遗漏的 1 页也不能变成不可管理的内存。

**Case 5：非法释放**
以下操作非法，应通断言或检查拒绝：
- `base == NULL`或者起始页号不是实际分配块大小的整数倍；
- `n == 0`；
- 释放已空闲的块；
- 从已分配块内部开始释放；
- 释放页数与记录的块大小不匹配；
- 释放保留页或未登记页。

### 5. buddy_nr_free_pages()
**Pre-Condition**
Buddy 已经初始化。

**Post-Condition**
直接返回当前真正处于空闲状态的物理页总数。。

**Requirements**
空闲块计数已在对块的操作中更新了。

### 6. buddy_check()

**Pre-Condition**
管理器已初始化且已有合法可用页区间。

**Post-Condition**
进行基本分配、释放及计数检查，检查结束后所有测试用页面均已归还。

**Requirements**
暂不进行实现。
````

**最终结果：**

**关键改进点总结：**

1. 不能只要求“正确登记空闲内存”，需要明确非 2 的幂长度、非对齐起点和多区间登记的边界条件。
2. 判断伙伴时使用全局页面下标，同时检查页面是否属于已经登记的可用范围。

##### 第三次迭代

**遇到的问题：**
- 申请页数 n 不是 2 的幂时，实际分配页数和原始请求页数不同。如果按 n 扣减空闲页数或在块头记录 n，释放时可能无法正确归还整个块。
- 释放时不能仅根据两个空闲块物理地址相邻就合并，还必须判断它们是否属于同一个父块；分配时也需要保留分裂后未使用的伙伴块。

**问题解决策略：**
- 在 `[SPECIFICATION]` 中明确申请 3 页实际分配 4 页、申请 5 页实际分配 8 页，要求分配块头 `property` 记录实际块大小；`free_pages()` 应比较向上取整后的释放大小与 `property`，空闲页数按实际块大小更新。

**关键改进点总结：**

1. 在 `[SPECIFICATION]` 中把实际分配块大小、块头 `property` 和空闲页计数的关系写清楚，将伙伴关系、合并条件及停止合并的情况分别说明，不用“相邻就合并”。

````markdown
**1. 物理内存管理器接口**
`kern/mm/pmm.h` 定义：
```c
struct pmm_manager {
    const char *name;
    void (*init)(void);
    void (*init_memmap)(struct Page *base, size_t n);
    struct Page *(*alloc_pages)(size_t n);
    void (*free_pages)(struct Page *base, size_t n);
    size_t (*nr_free_pages)(void);
    void (*check)(void);
};
```
`pmm.c` 通过全局 `pmm_manager` 指针调用上述接口。

```c
const struct pmm_manager buddy_pmm_manager;
```
其 `.check` 成员绑定 `buddy_check()`。

`pmm.c` 提供统一接口：
```c
struct Page *alloc_pages(size_t n);
void free_pages(struct Page *base, size_t n);
size_t nr_free_pages(void);
```

以及单页接口：
```c
#define alloc_page() alloc_pages(1)
#define free_page(page) free_pages(page, 1)
```

内核初始化流程为：
```
pmm_init() → init_pmm_manager() → page_init() → check_alloc_page()
```
- `init_pmm_manager()`：选择并初始化 Buddy 分配器。
- `page_init()`：完成物理内存探测、保留页排除及空闲页登记。
- `check_alloc_page()`：通过 `pmm_manager->check()` 调用 Buddy 的测试函数。

**2. 物理页描述符**
`kern/mm/memlayout.h` 定义：
```c
struct Page {
    int ref;
    uint64_t flags;
    unsigned int property;
    list_entry_t page_link;
};
```

相关标记：
- `PG_reserved`：表示该物理页被内核保留，不能分配。
- `PG_property`：表示该 `Page` 是一个空闲连续物理块的头页。
- `PageReserved(page)`：检查页面是否被保留。
- `PageProperty(page)`：检查页面是否为空闲块头。
- `page_ref(page)`：获取页面引用计数。

Buddy 中 `property` 的使用约定为：
- 空闲块头的 `property` 保存空闲块实际页数，并设置 `PG_property`。
- 分配成功后，分配块头清除 `PG_property`，但 `property` 仍保存实际分配块的页数，`property` 不保存原始申请页数。
例如申请 3 页：
```c
struct Page *p = alloc_pages(3);
```
如果分配成功，实际占用 4 页，分配块头应满足：
```c
assert(p->property == 4);
assert(!PageProperty(p));
```

**3. 地址转换及物理页范围**
`kern/mm/pmm.h` 提供：
- `pages`：物理页描述符数组起始地址。
- `npage`：物理页号上界。
- `nbase`：DRAM 起始物理页号。
- `page2ppn(page)`：获取物理页号。
- `page2pa(page)`：获取物理地址。
- `pa2page(pa)`：获取物理页描述符。
其中：
```c
page2ppn(page) = page - pages + nbase
```
页面大小为：
```c
#define PGSIZE 4096
#define PGSHIFT 12
```
对于成功分配的 `Page *p`，若实际块大小为 `size` 页，应满足：
- `nbase <= page2ppn(p) < npage`。
- `size <= npage - page2ppn(p)`。
- `page2ppn(p) % size == 0`。
- 分配块中的页不属于保留页。
实际块大小始终是 2 的幂。

**4. 多阶空闲链表**
Buddy 使用多阶空闲链表管理空闲块。
第 `k` 阶链表存放大小为 `2^k` 页的空闲块。
`libs/list.h` 提供：
- `list_entry_t`
- `list_init()`
- `list_empty()`
- `list_next()`
- `list_prev()`
- `list_add()`
- `list_del()`
`memlayout.h` 提供 `le2page(le, member)`，可以将链表节点转换为对应的 `struct Page *`。
测试中可以检查 Buddy 的各阶空闲链表，但具体变量名和最大阶数以当前 `buddy_pmm.c` 为准。

**5. 分配与释放的行为约定**
申请 n 页时，实际分配块大小应向上取整为最小的 2 的幂。
例如：
- `n = 1`，实际分配 1 页。
- `n = 2`，实际分配 2 页。
- `n = 3`，实际分配 4 页。
- `n = 5`，实际分配 8 页。

释放时将 n 向上取整后，与块头 `property` 记录的实际块大小比较；只要取整结果相同，释放时的 n 可以与申请时不同。
例如：
``` c
struct Page *p = alloc_pages(3);
free_pages(p, 3);
```
应归还完整的 4 页块，空闲页总数增加 4。
不允许对一个已分配块进行部分释放，也不允许从分配块中间的物理页开始释放。

**6. 伙伴关系**
只有同时满足以下条件的两个块才能合并：
1. 两个块大小相同，均为 2 的幂。
2. 两个块属于同一个更高阶块的两个子块。
3. 两个块都处于空闲状态。
4. 合并后的全部页面均属于已登记的可用内存。
两个物理地址相邻的空闲块不一定能够合并。

### 2. 基本物理页分配与释放检查
**Pre-Condition**
Buddy 中至少存在 3 个可分配的物理页，并且能够满足 3 次单页请求。

**Post-Condition**
- 三次单页分配均成功，分配的物理页互不相同。
- 每个分配块大小为 1 页，且不属于保留页。
- 分配后空闲页数减少 3。
- 释放后空闲页数恢复。

**Case 1：连续分配 3 个物理页**
连续调用 3 次 `alloc_page()`。
要求返回的 `p0`、`p1`、`p2` 均不为 `NULL`，并满足：
- `p0 != p1 && p0 != p2 && p1 != p2`。
- `page_ref(p0) == 0`，`page_ref(p1) == 0`，`page_ref(p2) == 0`。
- 三个页面都满足 `nbase <= page2ppn(page) < npage`。
- 三个页面均不具有 `PG_reserved` 和 `PG_property` 标志。
- 三个分配块头的 `property` 均为 1。

**Case 2：释放其中一个页面**
使用 `free_page(p1)`，要求空闲页数增加 1。
此时 `p0`、`p2` 仍为已分配状态，不能被错误地加入空闲链表。

**Case 3：再次分配一个物理页**
再次调用 `alloc_page()`，要求返回值不为 `NULL`，且不能等于仍被占用的 `p0` 或 `p2`。

**Case 4：释放全部测试页面**
释放所有尚未释放的页面，要求空闲页总数恢复到本项测试开始前。

**Requirements**
每次成功分配和释放后，空闲页计数应按实际分配块大小变化。
不能因为两个分配结果的起始地址不同，就忽略可能存在的物理页范围重叠问题。

### 3. 不同页数请求的分配检查
**Pre-Condition**
存在能够满足相应请求的空闲块。

**Post-Condition**
- 实际分配块大小是能够容纳 n 的最小 2 的幂。
- 分配块的起始物理页号按实际块大小对齐。
- 块头 `property` 保存实际分配页数。
- 空闲页总数减少实际分配块的页数，释放后恢复。

**Case 1：申请 2 页**
调用 `alloc_pages(2)`。
成功后应满足：
- `property == 2`。
- 起始物理页号能被 2 整除。
- `PageProperty(page)` 为假。
- 空闲页总数减少 2。
使用 `free_pages(page, 2)` 释放后，空闲页总数增加 2。

**Case 2：申请 3 页**
调用 `alloc_pages(3)`。
成功后应满足：
- `property == 4`。
- 起始物理页号能被 4 整除。
- `PageProperty(page)` 为假。
- 空闲页总数减少 4，而不是 3。
使用 `free_pages(page, 3)` 释放后，应归还全部 4 页。

**Case 3：申请 5 页**
调用 `alloc_pages(5)`。
成功后应满足：
- `property == 8`。
- 起始物理页号能被 8 整除。
- 空闲页总数减少 8，而不是 5。
使用 `free_pages(page, 5)` 释放后，应归还全部 8 页。

**Case 4：连续分配不同大小的块**
连续申请 1、2、3、5 页，记录每个成功分配块的起始物理页号及实际块大小。
对于任意两个块，其物理页号区间不能相交。例如申请 3 页的块应按实际占用的 4 页参与重叠检查。

**Case 5：不同 n 向上取整后块大小相同**
例如申请 5 页按 6 页释放，两次 n 向上取整后均为 8，应允许归还完整的 8 页块，空闲页总数恢复。

**Requirements**
不允许使用原始申请页数代替实际块大小计算空闲页变化和物理地址范围。
对于已经确定存在能够满足请求的空闲块的情况，如果分配返回 `NULL`，应触发断言。

### 4. 多阶空闲链表检查
**Pre-Condition**
Buddy 的各阶空闲链表已经初始化，并且管理着已登记的空闲物理页。

**Post-Condition**
各阶链表中的空闲块大小、页面标记和空闲页总数保持一致。

**Case 1：检查各阶空闲块**
遍历每个 k 对应的空闲链表。
第 k 阶链表中的每个块应满足：
- 该空闲块头具有 `PG_property` 标志。
- 头页的 `property == 2^k`。
- 起始物理页号能被 `2^k` 整除。
- 块的起始物理页号不小于 `nbase`。
- 块的结束位置不超过 `npage`。
- 块中不包含 `PG_reserved` 页面。

**Case 2：检查不同空闲块**
各阶链表中的空闲块不能互相重叠。
同一个空闲块头不能同时出现在不同 k 的空闲链表中。

**Case 3：检查空闲页总数**
统计所有 k 链表中空闲块的页数之和，要求：
```
所有空闲块的 property 之和 == nr_free_pages()
```

**Requirements**
此项检查只读取链表和页面信息，不修改分配器的内部状态。
在分裂、合并及多次分配释放之后，也应进行相同的检查。

### 5. 伙伴分裂检查
**Pre-Condition**
存在一个已确定的较高阶空闲块，且目标阶没有可直接分配的空闲块，需要从较高阶块分裂才能满足请求。

**Post-Condition**
- 较高阶块能够逐级分裂成大小相等的两个子块。
- 分配器得到符合请求大小的块。
- 未分配的子块仍保留在对应 k 的空闲链表中。
- 原父块不再作为完整空闲块存在。
- 空闲页总数只减少实际分配出去的页数。

**Case 1：从大块分裂出小块**
例如当前存在一个 16 页空闲块，目标阶没有 4 页或 8 页的空闲块，申请 4 页。
应能够通过分裂得到一个 4 页块，并保留未分配的 4 页和 8 页空闲块。

**Case 2：检查分裂后的链表**
要求：
- 原来的 16 页块不再留在对应阶数的空闲链表中。
- 新产生的 4 页和 8 页空闲块应进入各自对应的 k 链表。
- 新空闲块的 `property` 和 `PG_property` 标志正确。
- 已分配的 4 页块不能同时出现在空闲链表中。
- 分裂后的全部块互不重叠，页数之和没有变化，除去本次分配的 4 页后，其余页面仍为空闲。

**Case 3：再次分配**
在上述分裂后的受控内存区域中继续申请小块，应能够使用未分配的部分。
**Requirements**
必须确认本次分配确实使用了较高阶空闲块，不能仅因为 `alloc_pages(4)` 成功就认为已经检查了分裂。
可以通过比较分裂前后的各阶空闲块状态来判断。

### 6. 伙伴合并检查
**Pre-Condition**
存在两个大小相同、属于同一个父块的合法伙伴块，能够分别对它们进行分配和释放。

**Post-Condition**
- 只有两个伙伴都空闲时才能合并。
- 合并后的块大小为原来块大小的两倍。
- 被合并的子块不再单独保留在低阶空闲链表中。
- 如果合并后的块仍有合法的空闲伙伴，应能够继续向上合并。

**Case 1：只有一个伙伴空闲**
例如两个 4 页块构成一个 8 页父块。
当其中一个 4 页块仍被占用时，释放另一个 4 页块，不能形成一个完整的 8 页空闲块。

**Case 2：两个伙伴均被释放**
释放另一个 4 页块后，应能够合并为一个 8 页空闲块。
要求：
- 合并后的块大小为 8 页。
- 合并块头的 `property == 8`。
- 起始物理页号能被 8 整除。
- 原来的两个 4 页块不再作为两个独立块出现在低阶链表中。
- 空闲页数只按实际释放的页数增加，合并操作本身不增加空闲页数。

**Case 3：递归合并**
如果新形成的 8 页空闲块还有一个大小为 8 页的空闲伙伴，应继续合并为 16 页块。
检查合并后的块大小、头页标志及对应 k 链表，直到无法继续合并或达到最大 k。

**Case 4：两个块不是合法伙伴**
对于大小不同，或者虽然大小相同但不属于同一个父块的相邻空闲块，不能进行合并。
不能形成大小不是 2 的幂的空闲块，也不能把未登记页面或保留页合并进来。
特别检查两个同阶空闲块虽物理地址相邻、但属于不同父块时，不能错误合并。

**Requirements**
必须检查实际合并后的块及各阶链表状态，不能只通过空闲页总数恢复判断伙伴合并正确。

### 7. 分配失败检查
**Pre-Condition**
Buddy 已经初始化，当前空闲页数量能够通过 `nr_free_pages()` 获取。

**Post-Condition**
当不存在能够满足请求的空闲块时返回 `NULL`，空闲页总数及各阶空闲链表状态不变。

**Case 1：申请页数超过空闲页总数**
记录当前空闲页数 `nr_free`。
申请超过 `nr_free` 的页数，要求分配失败并返回 `NULL`。
分配前后的 `nr_free_pages()` 应相等。

**Case 2：总空闲页数足够但没有满足请求的块**
例如当前只有若干个相互分离的 2 页空闲块，空闲页总数不少于 4，但没有 4 页或更高阶的空闲块。
此时申请 4 页应返回 `NULL`。

**Case 3：检查失败后的状态**
分配失败后，各阶链表中的空闲块数量、块头地址、`property` 和空闲页总数应保持不变。
已经分配出去的块不能因为本次分配失败而重新进入空闲链表。

**Requirements**
对于第二种情况，需要先确认测试状态中确实不存在可分裂得到目标块的更高阶空闲块。
不得直接破坏真实内核空闲链表来构造测试场景。
对于 `n == 0`、重复释放、错误起始地址等会触发断言的非法调用，不应放入正常启动时必须成功返回的 `buddy_check()` 中。

### 8. 多次分配释放及最终状态检查
**Pre-Condition**
Buddy 中存在可用于测试的空闲物理页，且各阶链表状态正确。

**Post-Condition**
- 所有测试中分配的页面均已释放。
- 空闲页总数恢复到测试开始前。
- 各阶链表中的空闲块没有丢失、重复登记或重叠。
- 没有已分配页面仍被错误地计为空闲页。

**Case 1：不同顺序释放**
连续分配不同大小的块后，不按照分配顺序释放，而是交错释放。
每次释放后检查 `nr_free_pages()` 增加的数量是否等于对应块的实际大小。
尚未释放的块不能被错误地加入空闲链表。

**Case 2：重复分配和释放**
重复进行若干轮不同大小的分配、释放操作。
每一轮全部释放后，空闲页数应恢复到该轮开始前。

**Case 3：最终空闲页数检查**
记录 `buddy_check()` 开始时的空闲页数 `free_before`。
检查全部完成后，应满足：
```
nr_free_pages() == free_before
```

**Case 4：最终空闲链表检查**
再次遍历各阶链表，检查：
- 第 k 阶空闲块的大小仍为 `2^k`。
- 每个空闲块头的 `PG_property` 和 `property` 正确。
- 空闲块之间不重叠。
- 各阶空闲块的页数之和等于 `nr_free_pages()`。

**Requirements**
所有测试过程中分配的页面都必须归还。
如果为了测试分裂、合并或分配失败而临时修改了 Buddy 的测试状态，应在返回前完整恢复原有的空闲链表、空闲页计数和必要的 Page 信息。
不能只恢复空闲页数量，却留下错误的链表节点或页面状态。


### 9. `buddy_init_memmap()` 登记检查
**Pre-Condition**
- Buddy 已初始化；待登记页面具有 `PG_reserved` 标志，且尚未加入空闲链表。
- 测试不能破坏当前正在使用的物理页。

**Post-Condition**
输入区间内的 n 页全部登记，空闲块按自身大小对齐且互不重叠，空闲页总数增加 n，未登记区域不被加入空闲链表。

**Case 1：区间长度不是 2 的幂，起点未按大块对齐**
例如在 16 页对齐区域中登记偏移 4 页、长度 12 页的区间，应保留一个 4 页块和一个 8 页块，共登记 12 页，不包含前面未登记的 4 页。

**Case 2：多次登记相邻区间**
分次登记的相邻空闲块在满足同阶伙伴条件时应能够合并。检查空闲页数累计正确，合法伙伴最终可以合并成更高阶块。

**Case 3：多次登记不相邻区间**
例如分别登记偏移 0 和偏移 8 处各 4 页，中间 4 页未登记。应保留两个独立的 4 页块，不得跨越未登记区间合并；只有这些空闲页时，申请 8 页应返回 `NULL`。

**Requirements**
检查页面标志、块大小、对齐、各阶空闲链表和空闲页计数。测试结束后恢复原有管理状态，不得重复登记真实空闲页。

### 10. 非法释放检查
**Pre-Condition**
测试对象为已经成功分配且尚未释放的物理页块，已知其实际大小和起始页号。

**Post-Condition**
释放起始位置未对齐，或者 n 向上取整后与块头 `property` 不一致时，应触发相应断言，拒绝非法释放。

**Case 1：n 向上取整后小于实际块大小**
对实际大小为 4 页的分配块以 n = 2 释放，应触发块大小不匹配的断言。

**Case 2：n 向上取整后大于实际块大小**
对实际大小为 4 页且起始页号满足 8 页对齐的分配块以 n = 5 释放，应触发块大小不匹配的断言，而不是对齐断言。

**Case 3：释放起始页号未对齐**
对实际大小为 4 页的分配块，从起始页之后一页开始以 n = 4 释放，应触发起始页号未对齐的断言。

**Requirements**
三个 Case 分别进行预期触发断言的测试，默认不在正常 `buddy_check()` 中执行。应确认触发的是对应断言，不能把任意 panic 当作测试通过。不得修改 `buddy_free_pages()` 的原有逻辑。
````

#### 实现迭代过程

本模块的实现经历了 4 次迭代，过程如下：

---

##### 第一次迭代

**遇到的问题：**
- 普通分配和释放虽然可以通过断言检查返回值与空闲页数，但 Buddy 的分裂、合并需要确定具体空闲块的大小和位置，不能直接假设真实内存中的分配地址固定。

**问题解决策略：**
- 在第二份提示词的 `[SPECIFICATION]` 中补充各阶链表和页面状态检查；对需要固定布局的情况，要求使用从真实分配器申请的 16 页对齐受控区域，并在测试结束时恢复真实链表和空闲页计数。
- 在 `[RELY]` 中明确第 k 阶对应 `2^k` 页，并要求 AI 修正分裂后错误的阶数断言，同时检查剩余块地址、头页 `property`、`PG_property` 及空闲页数变化。

**最终结果：**
- 实现 `buddy_check()` 及基本分配、不同页数请求、多轮分配释放、空闲链表、分裂、合并和分配失败等测试函数。
- 修正测试断言后，编程 AI 报告 `make` 编译通过，QEMU 输出 `check_alloc_page() succeeded!`，测试正常返回。

**关键改进点总结：**

1. 不能只检查 `alloc_pages()` 是否返回非 `NULL`，还需要检查实际块大小、地址对齐、页面标志和各阶链表。
2. 在真实内存中不能假设固定返回地址；只有先确定测试区域的空闲块布局，才能检查分裂和合并后的具体位置。

---

##### 第二次迭代

**遇到的问题：**
- 初版测试使用原始申请页数释放，没有覆盖申请 n 和释放 n 不同、但向上取整后的块大小相同的合法情况。
- 原有不合并测试涉及不相邻的同阶块和相邻的不同阶块，没有直接检查两个物理地址相邻、大小相同但不是真正伙伴的块是否会被错误合并。

**问题解决策略：**
- 在补充提示词中要求 AI 修改 `buddy_sizes_check()`，增加同一取整区间的释放测试，如申请 3 页按 4 页释放、申请 5 页按 6、7、8 页释放，并检查 `property` 和空闲页数是否按实际块大小处理。
- 在补充提示词中要求 AI 修改 `buddy_no_merge_check()`，增加 16 页受控区域的四个 4 页块场景，先释放中间两个相邻但不属于同一父块的块，要求它们保持独立；随后释放合法伙伴，再检查能否逐级合并。

**最终结果：**
- 增加的两类测试均通过。合法的不同 n 释放能够归还完整块，空闲页数恢复；相邻但不是伙伴的两个 4 页块没有错误合并。
- 编程 AI 报告 `make` 编译通过，QEMU 继续输出 `check_alloc_page() succeeded!`，分配与释放算法代码未修改。

**关键改进点总结：**

1. `buddy_free_pages()` 检查的是 n 向上取整后的大小与块头 `property` 是否相等，不是原始 n 是否完全相同。
2. 两个空闲块即使同阶且物理地址相邻，也必须属于同一个父块才能合并。

##### 第三次迭代

**遇到的问题：**
- 前两轮测试主要检查分配、释放及伙伴操作，没有直接测试 `buddy_init_memmap()` 对非 2 的幂长度和非高阶对齐区间的处理。
- 多次登记相邻或不相邻区间时，既要检查合法伙伴能否合并，也要防止跨越未登记页面错误合并；直接使用真实空闲链表重新登记会破坏现有管理状态。

**问题解决策略：**
- 在 `[SPECIFICATION]` 中增加 `buddy_init_memmap()` 检查要求，说明要复用已有的 16 页受控区域，并按照 `buddy_init_memmap()` 的前置条件准备带有 `PG_reserved` 标志且未登记的页面。
- 在提示词中明确三个 Case：长度为 12 页、起点偏移 4 页的区间；分次登记可合并成 16 页的相邻区间；中间保留 4 页的不相邻区间。要求分别检查块大小、对应阶数、空闲页数和保留页状态。

**最终结果：**
- 新增 `buddy_init_memmap_check()` 并接入受控测试流程。12 页区间按对齐要求划分为 4 页和 8 页块；多次相邻登记最终合并为 16 页块；不相邻的两个 4 页块没有跨越未登记区间合并，申请 8 页返回 `NULL`。
- 编程 AI 报告编译通过，QEMU 中 `check_alloc_page() succeeded!` 正常输出。

**关键改进点总结：**

1. `init_memmap()` 必须登记输入范围内的全部物理页，但每个空闲块仍须为 2 的幂大小并按自身大小对齐。
2. 通过分次登记和保留页检查，可以验证合并既不会遗漏合法伙伴，也不会越过未登记区间。

##### 第四次迭代

**遇到的问题：**
- 正常执行的 `buddy_check()` 无法直接检验非法释放是否被拒绝，因为预期触发的断言会使内核停止运行。
- 测试释放页数向上取整后大于实际块大小时，如果起始位置不满足较大块的对齐条件，会先触发对齐断言，不能证明块大小比较本身正确。

**问题解决策略：**
- 在补充提示词中要求增加默认关闭的 `BUDDY_ILLEGAL_FREE_TEST`，用 1、2、3 分别选择“释放大小过小”“释放大小过大”“起始页号未对齐”三种负向测试，正常模式保持为 0。
- 在提示词中明确三种负向测试的输入条件：在 16 页对齐受控区域申请实际大小为 4 页的块，分别使用 `free_pages(page, 2)`、`free_pages(page, 5)` 和 `free_pages(page + 1, 4)`；前两种情况必须先满足起始地址对齐要求，第三种情况专门检查起始页号未对齐。

**最终结果：**
- 编程 AI 分别运行三个模式：模式 1、2 均在 `assert(base->property == (unsigned int)size)` 处按预期 panic；模式 3 在 `assert((index & (size - 1)) == 0)` 处按预期 panic。
- 恢复默认模式后，`make` 编译通过，QEMU 输出 `check_alloc_page() succeeded!`。三种 panic 是预期非法输入检查结果，不属于正常测试失败。

#### 测试覆盖与有效性

**1. 核心行为及检验依据**

| 测试内容 | 检查条件及检验目的 |
|---|---|
| 分配与对齐 | 申请 1、2、3、5 页，检查实际分配 1、2、4、8 页；`property` 记录实际大小、`PG_property` 清除，且 `page2ppn(p) % size == 0`、块位于 `[nbase,npage)`，验证向上取整、对齐和边界正确。 |
| 多块分配与计数 | 同时持有上述块，检查实际页号区间互不重叠，分配和释放分别按实际块大小减少、增加空闲页数，防止重复分配或计数错误。 |
| 多阶空闲链表 | 遍历各阶，检查块头 `property == 2^k`、`PG_property`、对齐、边界及块间不重叠；各阶 `nr_free` 与链表一致，块页数总和等于 `nr_free_pages()`，检测错阶、重复登记及计数错误。 |
| 块分裂 | 在仅有一个 16 页空闲块的区域申请 4 页，检查原块移除，剩余 4、8 页块进入对应阶；再申请 2 页，检查剩余 2 页伙伴的位置和阶数，验证逐级分裂且无块丢失。 |
| 伙伴合并 | 两个 4 页伙伴仅一个空闲时不得合并；全部释放后合并为 8 页，再释放其 8 页伙伴后合并为 16 页。检查旧块移除且合并不重复计数，验证递归合并。 |
| 状态恢复 | 乱序释放并多轮重复分配释放，检查占用块不进入空闲链表；全部释放后页数恢复，所有阶链表状态正确，检测页数丢失、重复计数及链表损坏。 |

**2. 边界情况及检验依据**

| 测试内容 | 检查条件及检验目的 |
|---|---|
| 非 2 的幂区间 | 用 `buddy_init_memmap()` 登记 `[arena+4,arena+16)` 共 12 页，检查形成起点分别为 `arena+4`、`arena+8` 的 4、8 页块，总数为 12，前 4 页仍为 `PG_reserved`，验证按全局页号对齐拆分且不越界。 |
| 分次登记 | 按 `[arena+4,4)`、`[arena,4)`、`[arena+8,8)` 登记，检查依次合并为 8、16 页；仅登记前 4 页及第 8—11 页时，中间 4 页仍保留，两个块不合并且申请 8 页返回 `NULL`，验证合并不依赖登记顺序且不跨越未登记区域。 |
| 相邻但非伙伴 | 将 16 页分为四个 4 页块，仅释放中间两个，检查仍为两个独立的第 2 阶块；释放两端后才合并为 16 页，验证合并依据伙伴关系而非单纯地址相邻。 |
| 分配失败 | 在 16 页区域申请 17 页，以及人工构造总空闲页数足够但只有 2 页阶块、无法提供 4 页块的状态，均应返回 `NULL`，且块头、链表和计数不变，验证容量不足与连续块不足时均能安全失败。 |
| 等价大小释放 | 申请 3 页按 4 页释放，申请 5 页按 6、7、8 页释放，检查取整结果相同且页数恢复，验证按块头 `property` 的实际大小校验，而非要求原始请求值相同。 |
| 非法释放 | 分别执行 `free_pages(base,2)`、`free_pages(base,5)`、`free_pages(base+1,4)`（均先申请 4 页），检查触发对应的大小或对齐断言，验证拒绝错误大小及块内起点释放。 |

**3. 为什么这些测试能够有效检验 Buddy System 实现**

测试同时检查**块大小为 2 的幂、对齐、分裂合并、链表状态及空闲页计数**，避免分配成功或总页数正确而内部可能有错误。

分裂、合并及失败测试使用可恢复的 16 页对齐受控区域，确保块位置和阶数确定；非法释放测试分别设置 `BUDDY_ILLEGAL_FREE_TEST=1/2/3`，核对预期断言并独立运行，避免内核停止影响正常测试。最终检查页数和链表恢复，确保不影响后续内存管理。

#### 关键调用路径与分支

```text
真实客户机写指令 → store helper → store_helper
  → 主表/victim 查询未命中 → tlb_fill
  → riscv_cpu_tlb_fill → get_physical_address
  → 权限与 PMP 检查 → tlb_set_page
  → tlb_set_page_with_attrs → 返回并执行实际写入
```

重点源码是 `target/riscv/cpu_helper.c` 与 `accel/tcg/cputlb.c`。`get_physical_address()` 先处理特权模式，再按 `satp.MODE` 区分 Bare 和 Sv39。Sv39 检查虚拟地址规范性，然后读取 PTE，判断有效位、叶子或非叶子、权限组合、U/S 访问、超级页对齐及 A/D 位。只有有效的非叶子项才继续下降；翻译或保护失败会产生异常。TLB 未命中还可能先在 victim cache 命中，不能将每次主表未命中都写成立即遍历页表。

选择 S 模式访存还有一个原因：M 模式本身存在直接地址路径并受 MPRV 等状态影响，若直接比较固件访问与内核访问，容易把特权模式差异误判为分页开关差异。条件断点还应约束访问类型，保证观察的是所选的真实写操作，而非取指或调试器读内存。

#### 真实访存的 VA→PA 计算

丁欣怡捕获分页前 `sd a0,0(t0)` 向 `0x80206000` 写 hartid，此时 `satp=0`；分页后捕获 `kern_init → memset` 的 `sb a1,-1(a5)`，有效数据 VA 为 `0xffffffffc0206018`。指令地址与指令访问的数据地址是两个对象。

Sv39 时 `satp=0x8000000000080205`，MODE 为 8，根表 PA 为 `0x80205000`。第一轮根索引 `(VA >> 30) & 511 = 511`，PTE 地址为 `0x80205ff8`，读出 `0x200000cf`。其 V/R/W/X/A/D 均置位、U 为零，PPN 为 `0x80000`，是合法根级叶子，映射 1 GiB。故本次第一轮就结束，并没有读取三张页表；“Sv39 三级”表示最大层数。

完整地址按超级页关系得到：

```text
PA = 0x80000000 | (VA & 0x3fffffff)
   = 0x80206018
```

`get_physical_address()` 在该 Sv39 路径的输出参数是 4 KiB 页基址 `0x80206000`，调用者结合原始页内偏移 `0x18` 完成访问；函数的整型返回值才表示成功或失败。[宿主单步输出](#validation-excerpts) 含 Bare、Sv39 两次 `HOST_WALK_PASS`，具体地址随内核构建变化，不能硬编码到后续复现实验。

#### 软件 TLB、Bare 与真实硬件的区别

Bare 不进行 Sv39 页表转换，但 QEMU 仍可填软件 TLB，将客户机物理地址快速对应到宿主内存。Sv39 则先完成客户机 VA→PA，再建立快速访问信息。QEMU 项中包含读、写、取指标签及 `addend`；普通 RAM 命中时，客户机地址加 `addend` 可定位宿主存储。它不是内核的 `va_pa_offset`，还会随宿主内存布局变化。

真实硬件 TLB 缓存翻译和权限等信息，不需要 QEMU 的宿主指针。不能据模拟器结构推断真实芯片的替换策略。当前页表叶子映射 1 GiB，而 QEMU 4.1.1 此路径按访问对应的 4 KiB 子页填软件 TLB，两者属于不同粒度。

在 `get_page_addr_code` 的 C 层查询处单步：标签匹配后越过 refill 分支，获得三次 `TLB_HIT_PASS`。这是后续内核取指的命中证据，不能写成 BSS 数据写第二次命中。TCG 普通数据命中快路径常直接生成为宿主机器码，并非每次访问都进入 C helper。

#### 实际问题与 AI 协作收获

最有价值的定位是从“固件有输出”继续追问内核是否真正执行，通过客户机 PC、`satp`、`stvec` 和旧版异常日志定位分页入口问题，再用新旧两版启动交叉验证。其他实际问题包括旧 QEMU 缺少 flex/bison、WSL 挂载盘解压慢，以及误读函数输出页基址。

AI 参与规格细化、源码路径检索、条件断点与脚本编写，并根据真实日志协助定位修正。有效的方法是用一条实际访存将指令、寄存器、PTE、物理地址与 TLB 分支串起来，再核对每一步证据；不能把源码分析中未触发的异常分支写成实测。该实验加深了对地址翻译、权限和缓存的理解，尚未涉及进程私有地址空间、缺页换入或多核 TLB shootdown。

#### 5.5.2 内核启动与启动映射核算

首先在终端二设置物理入口断点。此时尚未进入高地址映射，使用启动装载地址定位第一条内核指令，能够在参数保存和分页配置前读取初始状态：

```gdb
thbreak *0x80200000
continue
x/12i $pc
info registers pc sp a0 a1
p/x $satp
```

![图 G1：物理入口、参数寄存器和 Bare 状态](images/gdb-20261026/01-physical-entry.png)

在物理入口 `0x80200000` 设置一次性硬件断点后，读得 `pc=0x80200000`、`satp=0`、`a0=0`、`a1=0x87e00000`。此时地址转换处于 Bare 模式，`a0` 和 `a1` 分别传入启动 hart ID 与 DTB 地址。反汇编中的两条 `sd` 指令用于保存这两个参数；断点位于首条指令，参数保存尚未执行。`sp=0x80046eb0` 表明程序仍沿用此前的栈指针，尚未设置内核启动栈。由于内核 ELF 按高虚拟地址链接，GDB 在该低地址入口未显示函数符号。

接着仍在终端二设置 `paging_enabled` 断点。该位置处于分页配置和高地址转移之后、启动栈设置之前，便于将地址空间转换与栈初始化两个阶段分开观察：

```gdb
thbreak paging_enabled
continue
info registers pc sp
p/x $satp
x/10i $pc
p/x (unsigned long)&boot_page_table_sv39
set $root_pa = ((unsigned long)$satp & 0xfffffffffff) << 12
p/x $root_pa
x/gx (unsigned long)&boot_page_table_sv39 + 511*8
```

![图 G2：进入 paging_enabled 并读取 satp 和根 PTE](images/gdb-20261026/02-paging-enabled.png)

继续运行至 `paging_enabled` 后，PC 变为 `0xffffffffc020004c`，`satp=0x8000000000080206`。其 MODE 字段为 8，对应 Sv39；低 44 位保存根页表物理页号，左移 12 位得到根页表 PA `0x80206000`。根页表符号 VA 为 `0xffffffffc0206000`，与该物理地址相差 `0xffffffff40000000`。

根表第 511 项位于 VA `0xffffffffc0206ff8`，读得 PTE 为 `0x200000cf`。此时程序停在 `sfence.vma`，设置栈指针的 `lui sp,0xc0206` 尚未执行，因此仍可观察到低地址 `sp`。反汇编中 `jr t0` 后显示的 `unimp` 不在该跳转的顺序执行路径上，本图未显示非法指令异常。

随后以 `kern_init` 为断点，检查汇编启动代码是否已转入 C 初始化，并观察函数序言后的栈指针：

```gdb
thbreak kern_init
continue
info registers pc sp
p/x &bootstacktop
list
```

![图 G3：kern_init 的 PC、栈指针和 C 初始化入口](images/gdb-20261026/03-kern-init.png)

进入 `kern_init` 后，断点位于 `0xffffffffc020010e`，即函数入口后 8 字节，准备执行 BSS 清零。此时 `sp=0xffffffffc0205fe0`，比 `bootstacktop=0xffffffffc0206000` 低 `0x20` 字节，与函数序言分配栈帧的行为一致，说明程序已使用内核高地址栈。

图 G2、G3 中分别保留了表达式被拆行、误输入 Markdown 反引号所产生的命令错误；随后重新输入命令均获得有效输出。这些错误发生在 GDB 命令解析阶段，不影响上述寄存器和页表读数。

保持客户机暂停，在终端二读取根页表并进行两种地址计算。该操作读取已有状态，不调用分配器或地址翻译函数：

```gdb
set $va = (unsigned long)&kern_init
set $vpn2 = ($va >> 30) & 0x1ff
set $root_pte = *(unsigned long *)((unsigned long)&boot_page_table_sv39 + $vpn2*8)
p/x $va
p/d $vpn2
p/x $root_pte
p/x $root_pte & 0xff
set $pa = (($root_pte >> 10) << 12) | ($va & 0x3fffffff)
p/x $pa
p/x $va - 0xffffffff40000000

```

![图 G4：核对 kern_init 虚拟地址对应的物理地址](images/gdb-20261026/04-sv39-address-check.png)

选择函数符号地址 `&kern_init=0xffffffffc0200106` 核算映射。该地址与图 G3 中断点处的 PC 相差 8 字节。根索引为 `(VA >> 30) & 0x1ff = 511`，对应 PTE 的低八位为 `0xcf`，其中 V、R、W、X、A、D 置位，U、G 清零。该项为根级叶子，其物理页号满足超级页对齐要求，对应 1 GiB 映射。

根据根级叶子的地址组成关系：

```text
PA = ((PTE >> 10) << 12) | (VA & 0x3fffffff)
   = 0x80000000 | 0x00200106
   = 0x80200106
```

使用固定偏移计算 `VA - 0xffffffff40000000`，结果同为 `0x80200106`，GDB 等值比较返回 1。两种计算一致，验证了所选函数地址的启动映射关系。该映射在根级叶子处完成解析，本项观察属于客户机页表内容核算，未涉及宿主 MMU 函数或 TLB 查询过程。

#### 5.5.4 Best-Fit 分配选择、分裂与回收

为比较分配前后的链表，在终端二定义只读命令 `show_best`，显示空闲页总数及最多 20 个空闲块的首页地址、块长和标志。命令只读取描述符，不改变分配器状态：

```gdb

set $bf_seen = $bf_seen + 1

end
```

首先将断点限定为 `n==5`，跳过前面的单页自检，捕获原自检中的连续 5 页申请。`finish` 后立即保存 `a0`，因为 RISC-V ABI 通过该寄存器返回分配得到的指针：

![图 G7：从初始大块分配 5 页](images/gdb-20261026/07-best-fit-split.png)

在 `best_fit_alloc_pages(n=5)` 停下时，调用栈显示该请求来自 `best_fit_check → alloc_pages → best_fit_alloc_pages`。分配前，空闲链表中仅有一个首页为 `0xffffffffc0210340`、长度为 31928 页的块。分配返回同一首页，其 `flags` 与 `property` 均清零；剩余空闲块首页变为 `0xffffffffc0210408`，长度为 31923 页，空闲总数恰好减少 5。

两个首页指针相差 `0xc8=200=5×40` 字节，对应 5 个 `Page` 描述符，即分配块占用的 5 个连续物理页。剩余块从原块的第 6 个页面开始，符合分配前部并保留余部的分裂方式。

继续在终端二设置条件断点 `n==1 && nr_free==3`。在当前自检顺序下，该条件定位到包含 2 页块和 1 页块的选择场景；随后用 `show_best` 确认候选集合，才能解释返回地址所体现的策略：

```gdb

continue

show_best
finish
```

![图 G8：在 2 页块和 1 页块中选择精确匹配者](images/gdb-20261026/08-best-fit-selection.png)

在选择策略测试中，链表按地址顺序包含两个空闲块：`0xffffffffc0210368` 对应 2 页，`0xffffffffc02103e0` 对应 1 页。申请 1 页后，返回后者，剩余链表仅保留 2 页块，空闲总数由 3 变为 2。

地址较低的 2 页块已经能够满足请求，但实际选择了容量恰好匹配的 1 页块，符合 Best-Fit 的最小适合块规则。对于这一候选集合，First-Fit 将选择先遇到的 2 页块，因此该场景能够区分两种策略。

释放阶段选择 `n==5` 且空闲页数大于零的调用，以定位当前自检恢复全局空闲链表后的归还操作；再进入 `best_fit_insert_free_block`，将释放入口、插入前和插入后的状态对应起来：

```gdb
p n
```

![图 G9：归还 5 页并与后继空闲块合并](images/gdb-20261026/09-best-fit-coalesce.png)

释放时，待归还块首页为 `0xffffffffc0210340`，请求释放 5 页；空闲链表中的后继块首页为 `0xffffffffc0210408`，长度为 31923 页。进入 `best_fit_insert_free_block` 后，归还块已设置 `flags=2`、`property=5`。两首页相差 5 个描述符，满足 `base + base->property == successor`，因此能够合并。

函数返回后，链表恢复为首页 `0xffffffffc0210340`、长度 31928 页的单个块，空闲总数增加 5。该结果与源码中“释放函数更新计数、插入函数调整链表和块长”的分工一致，观察到的后继合并没有造成重复计数。

![图 G10：Best-Fit 的 DTB、布局与自检成功](images/gdb-20261026/10-best-fit-self-check.png)

串口显示管理器为 `best_fit_pmm_manager`，并输出 `check_alloc_page() succeeded!`。描述符数组 PA、可用起点和空闲页数分别为 `0x80208000`、`0x80348000` 和 31928，与图 G6—G9 一致。

选择 `0x80200008` 是因为本次反汇编在此处显示 `sd a0,0(t0)`，用于保存启动 hart ID。断点停在存储执行前，便于取得实际地址并为宿主设置条件断点。重新构建后，应先在入口停下并反汇编，重新确认指令地址。

终端三附加到终端一对应的进程：

```bash
sudo gdb -q -nx \
  /mnt/d/操作系统/Lab2-A/lab2/_local/qemu-build/riscv64-softmmu/qemu-system-riscv64 \
  -p "$(cat /tmp/lab2-qemu-hostdebug.pid)"
```

本次普通用户执行 `attach` 时受到 `ptrace` 权限限制，改用上述命令后成功附加。附加时停在 `ppoll` 且提示缺少 glibc 源文件，不影响随后在已具备源码和符号的 QEMU 函数中调试。

终端切换只改变输入位置。每次应先在终端三设置宿主断点并执行 `continue`，使 QEMU 进程恢复运行，再在终端二执行 `si` 触发客户机访存。宿主断点命中后，终端二的单步请求可能仍在等待；应在终端三完成观察并继续运行后，再等待终端二返回提示符。只有出现 `(gdb)` 提示符时才输入下一条命令。

#### 5.6.2 Bare 状态下的存储与 TLB 填充

在终端二的存储指令断点处查询：

```gdb
x/i $pc
info registers pc t0 a0
p/x $satp
```

![图 H1：Bare 状态下保存 hart ID 的客户机存储指令](images/host-gdb-20261027/01-bare-guest-store.png)

图 H1 显示 `PC=0x80200008`，指令为 `sd a0,0(t0)`，`t0=0x80207000`、`a0=0`、`satp=0`。因此此次操作是向客户机地址 `0x80207000` 写入 8 字节的零值，尚未启用 Sv39。

在终端三设置条件断点并恢复宿主，然后切换到终端二执行一次 `si`：

```gdb
set pagination off
break get_physical_address if addr == 0x80207000 && access_type == 1 && mmu_idx == 1
continue
```

断下后在终端三检查调用栈与参数：

```gdb
bt 7
p/x addr
p/x env->satp
```

![图 H2：Bare 存储进入 QEMU 地址翻译慢路径](images/host-gdb-20261027/02-bare-host-translation.png)

调用栈由 TCG 生成代码进入 `helper_le_stq_mmu → store_helper → tlb_fill → riscv_cpu_tlb_fill → get_physical_address`。`size=8` 与客户机的 `sd` 对应；`access_type=1` 对应 `MMU_DATA_STORE`，`mmu_idx=1` 对应本次 S 模式访问。地址与图 H1 一致，说明该断点来自所选客户机存储。写访问条件也排除了调试器读取内存所产生的读访问。

根据 `cpu_helper.c`，此处 S 模式不会进入 M 模式的直接返回分支，而是在解析 `satp.MODE=0` 后进入 Bare 分支，将输入地址作为物理地址返回。随后在终端三观察填充入口：

```gdb
tbreak tlb_set_page_with_attrs if vaddr == 0x80207000 && mmu_idx == 1
continue
bt 5
p/x vaddr
p/x paddr
p/x size
```

![图 H3：Bare 地址的恒等映射进入软件 TLB 填充函数](images/host-gdb-20261027/03-bare-tlb-fill.png)

图 H3 中 `vaddr=paddr=0x80207000`，`size=0x1000`，`prot=7`。Bare 不查 Sv39 页表，但 QEMU 仍通过软件 TLB 保存快速访问信息，以便将客户机地址关联到宿主内存。这里的恒等关系仅指客户机虚拟地址与客户机物理地址，不能将其解释为宿主进程中的指针地址。

#### 5.6.3 Sv39 状态下选取 BSS 清零指令

在终端三执行 `continue`，等待终端二的单步返回。终端二随后定位 `memset`：

```gdb
thbreak memset
continue
disassemble /r memset
thbreak *0xffffffffc0202626
continue
x/i $pc
info registers pc a5 a4 satp
p/x &edata
```

本次反汇编显示 `memset+46` 即 `0xffffffffc0202626` 为 `sb a4,0(a5)`。选取循环体中的字节存储，可以将实际写入地址与 `kern_init()` 中的 `memset(edata, 0, end - edata)` 对应起来；函数入口还包含保存寄存器等栈访问，不宜直接当作 BSS 写入现场。

![图 H4：Sv39 状态下向 BSS 起点写入零字节](images/host-gdb-20261027/04-sv39-guest-store.png)

图 H4 显示 `a5=&edata=0xffffffffc0207018`、`a4=0`、`satp=0x8000000000080206`。该存储写入一个零字节，MODE 为 8，即 Sv39。GDB 将 BSS 起点显示为同地址的 `free_area` 符号，不代表此时已进入分配器初始化。图中的局部变量 `n=95` 与原始长度 96 字节并不矛盾：进入第一次循环体前，`while (n-- > 0)` 已对局部计数执行一次递减。

保持终端二停在存储前，在终端三按 Ctrl+C 暂停宿主进程，添加新的条件断点并继续：

```gdb
break get_physical_address if addr == 0xffffffffc0207018 && access_type == 1 && mmu_idx == 1
continue
```

再切换到终端二执行 `si`。宿主命中后，在终端三查询：

```gdb
bt 7
p/x addr
p access_type
p mmu_idx
p/x env->satp
```

![图 H5：Sv39 字节写入触发地址翻译](images/host-gdb-20261027/05-sv39-host-translation.png)

图 H5 的 `helper_ret_stb_mmu`、`size=1` 和 `val=0` 与图 H4 的 `sb` 一致。实际数据访问进入 `tlb_fill` 慢路径后调用地址翻译函数；这不是客户机发生了缺页异常，成功翻译后仍可继续执行原指令。

#### 5.6.4 根级叶子项与物理页基址

在终端三用 `next` 推进到相应赋值语句执行之后，再读取局部变量。本次文字调试记录得到以下数值，七张截图未单独保存这一组中间状态：

| 观察量 | 本次结果 | 含义 |
| --- | --- | --- |
| `mode`、`vm` | 1、8 | S 模式、Sv39 |
| `base` | `0x80206000` | 根页表物理地址，由 satp 的 PPN 左移 12 位得到 |
| `levels`、`ptidxbits`、`ptesize` | 3、9、8 | 最多三级、每级索引 9 位、每项 8 字节 |
| `i`、`ptshift` | 0、18 | 从根级开始；低两级 VPN 共 18 位 |
| `pte_addr` | `0x80206ff8` | 根表第 511 项的物理地址 |
| `pte`、`ppn` | `0x200000cf`、`0x80000` | 读出的页表项及其 PPN |
| `*physical` | `0x80207000` | 翻译函数输出的物理页基址 |

根级索引按 `(addr >> 30) & 0x1ff` 计算为 511，故 PTE 地址为 `0x80206000 + 511 × 8 = 0x80206ff8`。本次在初始化尚未完成时查询 `idx` 曾读到无效旧值，随后宿主指令执行中的 `rax=0x1ff` 与上述计算吻合；已完成赋值的 `pte_addr` 也验证了索引结果。

在本地 QEMU 4.1.1 源码中，可按以下顺序推进到读取和计算完成的位置：

```gdb
until 252
next
p/x pte
next
p/x ppn
p i
until 334
next
p/x *physical
```

第 252 行调用 `ldq_phys(cs->as, pte_addr)`，`next` 后停在第 254 行时，`pte` 已读出，但 `ppn` 尚未赋值。再执行一次 `next` 才能读取 `ppn`。类似地，第 334 行执行之后才能读取 `*physical`。`list` 只显示源码，不推进程序；停在某行通常表示该行的语句即将执行。上述行号适用于本次 QEMU 源文件，换版本后应按语句重新定位。

PTE 低位 `0xcf` 表示 V、R、W、X、A、D 置位，U 未置位。该项在根级已具备读写执行权限，是 1 GiB 叶子映射，不需要继续查下两级页表。`ppn & ((1 << 18) - 1) = 0` 满足超级页对齐要求；本次 S 模式写访问具备权限，且 A/D 已置位，无需进入页表项原子更新分支。

第 334 行的计算为：

```text
vpn = 0xffffffffc0207018 >> 12
vpn & ((1 << 18) - 1) = 0x207
physical_page = (0x80000 | 0x207) << 12 = 0x80207000
page_offset = 0x18
完整客户机物理地址 = 0x80207000 + 0x18 = 0x80207018
```

`*physical` 是该 Sv39 路径返回的页基址；函数本身的整型返回值表示翻译是否成功。完整物理地址也等于客户机 VA 减去固定偏移 `0xffffffff40000000`，与启动汇编建立的映射一致。

#### 5.6.5 TLB 填充参数与客户机恢复执行

在终端三的翻译函数返回前设置填充断点：

```gdb
tbreak tlb_set_page_with_attrs if paddr == 0x80207000 && mmu_idx == 1
continue
info args
```

![图 H6：Sv39 翻译结果进入软件 TLB 填充入口](images/host-gdb-20261027/06-sv39-tlb-fill.png)

图 H6 的十进制参数转换为十六进制后为：

| 参数 | 本次值 | 解释 |
| --- | --- | --- |
| `vaddr` | `0xffffffffc0207000` | 客户机访问地址向下对齐到 4 KiB |
| `paddr` | `0x80207000` | 本次翻译得到的物理页基址 |
| `prot` | 7 | QEMU 的读、写、执行权限组合 |
| `mmu_idx` | 1 | 本次 S 模式访问使用的 MMU 索引 |
| `size` | 4096 | 本次软件 TLB 填充调用的页粒度 |

`riscv_cpu_tlb_fill()` 在翻译成功后，以 `address & TARGET_PAGE_MASK`、`pa & TARGET_PAGE_MASK` 和 `TARGET_PAGE_SIZE` 调用 `tlb_set_page()`，随后进入图中的函数。因此，根级叶子映射范围为 1 GiB 与该填充调用的 4 KiB 粒度并不矛盾：前者是客户机页表的映射范围，后者是这个 QEMU 实现为当前访问建立软件缓存的粒度。

图 H6 保存的是填充函数入口参数，尚不是读取已写入 TLB 项的截图。在终端三执行 `continue` 后，终端二的单步完成，查询客户机现场：

```gdb
x/8i $pc
info registers pc a0 a1 a2
```

![图 H7：地址翻译和填充路径返回后，客户机推进到下一条指令](images/host-gdb-20261027/07-guest-store-completed.png)

图 H7 中 PC 从存储指令 `0xffffffffc0202626` 推进到 `0xffffffffc020262a`，当前指令为 `ld a5,-56(s0)`，对应下一轮循环条件的计数读取。它与图 H4 构成一次存储前后的执行位置对照。`a0=0xffffffffc0207018`、`a1=0`、`a2=0x60` 与本次 `memset` 的初始参数一致；循环中的剩余计数已保存在栈上，不能把仍为 96 的 `a2` 当作当前剩余字节数。

本次证据覆盖 Bare 恒等翻译、Sv39 根级叶子解析、物理页基址计算、软件 TLB 填充入口及客户机单步返回。它未直接记录后续访问的 TLB 命中快路径，也未检查本次填充后的内部标签或 `addend` 字段，因此不据此声称“第二次数据写已命中 TLB”。第 5.4 节的历史取指命中记录仍属于另一组实验。此次未重新运行课程评分或分配器测试。

## 六、实验总结与收获

### 6.1 对操作系统的理解

| 本实验知识点 | OS 原理对应 | 含义、关系与差异 |
| --- | --- | --- |
| DTB、上界与保留区 | 物理资源发现与保护 | 已知 RAM 不等于全部可分配，还要排除固件、内核和元数据 |
| Page 数组与自举 | 资源元数据管理 | 描述符不是物理页本身，管理内存也会消耗内存 |
| First-Fit／Best-Fit | 动态分区选择与外部碎片 | 本实验以页为单位，选择策略不同；相邻合并不能跨占用页 |
| Buddy 取整、分裂与合并 | 分级分配与内部碎片 | 只有同阶伙伴能合并，请求 5 页占 8 页带来容量浪费 |
| pmm_manager 回调 | 公共接口与分配策略 | 不同策略可接入同一入口，但容量和释放语义仍须明确 |
| Sv39、PTE 和 satp | 虚拟地址翻译与权限 | 最大三级不等于每次查满三级，本例根级叶子形成 1 GiB 映射 |
| 软件 TLB 与 Bare | 缓存及模拟器实现 | QEMU 还需将客户机地址关联宿主内存，不能等同于真实硬件缓存结构 |
| 断言和状态恢复 | 系统不变量验证 | 不只检查返回非空，还需检查范围、计数、关系和测试自身不泄漏资源 |

OS 原理中重要但本实验尚未完整实现的内容包括：进程私有地址空间及切换、按需分页、页面置换和交换、写时复制、多核内存分配同步与 TLB shootdown、完整硬件内存保留表与热插拔，以及任意大小对象分配。

### 6.2 AI 协作开发的经验

明确真实接口比只描述算法名更重要。丁欣怡先区分 VA、PA、PPN 和描述符并规定初始化布局；贺翰林将测试直接操作的链表状态写入规格；刘泽民将算法和测试分成两份提示词，明确实际容量、伙伴关系和恢复条件。它们共同减少了“代码看起来合理但违反框架约定”的风险。

调试时应让结果与证据对应：丁欣怡用真实指令、PTE 和分支解释翻译，不以固件输出代替内核运行；刘泽民把错误阶数预期识别为测试问题，没有为让断言通过而修改分配算法；贺翰林区分模块生成、管理器切换和最终集成，不编造算法失败次数。三种非法释放也必须核对具体断言，不能把内核任意停止算作通过。
