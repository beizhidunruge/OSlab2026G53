## 一、实验目的

本实验的主要目的是理解 RISC-V 中断和异常的处理过程。

1. 理解 Trap 发生时处理器会记录哪些信息，内核又是怎么进入对应的处理程序的。
2. 掌握怎样在栈上保存和恢复寄存器，并把保存的 `trapframe` 传给 C 语言处理函数。

## 三、实验整体逻辑分析

### 2.1 本章节的逻辑主线

在实验 2 的基础上，这次要让内核能处理中断和异常。比如时钟事件到了，或者执行到一条断点指令，处理器会先转到 `stvec` 指定的入口。内核先保存当时的寄存器值，再根据 Trap 的原因进行处理。处理完以后，把寄存器恢复好，从 `sepc` 指定的位置接着执行。

模块 1 负责汇编入口、传参和返回，模块 2 根据传进来的 `trapframe` 处理中断或异常。比如断点异常要跳过触发异常的指令，模块 2 就修改 `tf->epc`，模块 1 在返回前把修改后的值写回 `sepc`。

### 2.2 功能的逐步实现

1. 先看框架里已有的 `idt_init()` 和 `SAVE_ALL`。`idt_init()` 将 `stvec` 指向 `__alltraps`，`SAVE_ALL` 在当前栈上保存现场。后面从哪里读寄存器、传给 C 函数的地址是什么，都要先看这里是怎么存的。
2. 然后补全 `__alltraps` 中调用 `trap()` 的部分，以及 `__trapret` 用到的 `RESTORE_ALL`。这样发生 Trap 后，可以把栈上的 `trapframe` 交给 C 函数，处理完再恢复现场并执行 `sret`。
3. 有了入口和返回，再在 C 代码里根据 `tf->cause` 分发。时钟中断需要累加 `ticks`，设置下一次时钟事件，并按要求输出和关机。断点和非法指令异常需要输出对应信息，再按指令长度调整 `tf->epc`。

### 功能模块：Trap 上下文恢复与 Trap 入口功能

**负责人：** 学号-姓名

#### 模块功能描述

我需要补全 `kern/trap/trapentry.S` 中的 `RESTORE_ALL` 宏和 `__alltraps` 入口。汇编部分调用的 C 函数在 `kern/trap/trap.c` 中，接口如下。

```c
void trap(struct trapframe *tf);
```

中断和异常都从 `__alltraps` 进入。原有的 `SAVE_ALL` 先把现场存到栈上，接下来由 `__alltraps` 把这个地址传给 `trap()`。返回后进入 `__trapret`，用 `RESTORE_ALL` 读出栈上的值，再用 `sret` 回到原来的执行流。

#### 核心代码实现思路

##### 1. 对照 `SAVE_ALL` 和 `struct trapframe`

我先看了 `SAVE_ALL` 中每条 `STORE` 的偏移，再和 `kern/trap/trap.h` 中的结构体对应起来。RV64 中 `REGBYTES` 是 8，前面 32 项按 `x0` 到 `x31` 排列，后面 4 项保存 CSR，一共占 `36 × 8 = 288` 字节。

| 字段 | 保存的值 | 相对 `trapframe` 起点的字节偏移 |
|---|---|---|
| `gpr` | `x0` 到 `x31` | 0 到 248，每项 8 字节 |
| `status` | `sstatus` | 256 |
| `epc` | `sepc` | 264 |
| `badvaddr` | `sbadaddr` | 272 |
| `cause` | `scause` | 280 |

`x2` 就是 `sp`。分配这 288 字节前，`SAVE_ALL` 先把原来的 `sp` 写入 `sscratch`。分配后用 `csrrw` 把原值读到 `s0`，再存到偏移 `2*REGBYTES` 的位置，这就是 `gpr.sp`。

##### 2. 在 `__alltraps` 中调用 `trap()`

```asm
mv a0, sp
jal trap
```

执行完 `SAVE_ALL` 后，此时的 `sp` 就是 `trapframe` 的地址。RISC-V 调用约定用 `a0` 传第一个参数，所以把 `sp` 复制给 `a0` 就能调用 `trap()`。288 字节是 16 的倍数，原栈的 16 字节对齐在分配后仍然成立。`trap()` 返回时把 `sp` 恢复到调用前的位置，`jal` 的返回地址就是后面的 `__trapret`。

##### 3. 在 `RESTORE_ALL` 中恢复现场

先从当前 `trapframe` 取出 `status` 和 `epc`，借用 `s1` 和 `s2` 写回对应的 CSR。

```asm
LOAD s1, 32*REGBYTES(sp)
LOAD s2, 33*REGBYTES(sp)
csrw sstatus, s1
csrw sepc, s2
```

这里取的是 `trap()` 处理后的值。例如断点处理更新了 `tf->epc`，这里写回的就是更新后的返回地址。随后按保存时的偏移恢复 `x1`、`x3` 到 `x31`，包括刚才用到的 `s1` 和 `s2`。`x0` 的值固定为 0。

最后执行 `LOAD x2, 2*REGBYTES(sp)`。前面的加载都要用当前的 `sp` 找到 `trapframe`，所以要等它们读完再换回原来的 `sp`。接着 `__trapret` 执行 `sret`，处理器按 `sstatus.SPP` 确定返回的特权级，把 `SPIE` 的值恢复到 `SIE`，并从 `sepc` 指定的地址继续执行。

用 LLVM 生成 RV64 目标文件，再核对反汇编。下面是其中几条指令。

```text
0004: addi sp, sp, -288
0062: mv a0, sp
0064: jal 0
0068: ld s1, 256(sp)
006a: ld s2, 264(sp)
006c: csrw sstatus, s1
```

## 六、实验总结与收获

### 对操作系统的理解

1. **中断和异常。** 时钟中断来自定时器，是异步事件。断点和非法指令异常由当前指令触发，是同步事件。在 RISC-V 里它们都属于 Trap，可以先走同一个入口，再根据 `scause` 区分原因。
2. **现场的保存和恢复。** OS 原理里讲的保存现场，在这次实验中就是由处理器记录返回位置和状态，再由 `SAVE_ALL` 把通用寄存器和相关 CSR 存到栈上。处理完成后，汇编代码把需要的值恢复好，处理器执行 `sret` 完成返回。之前只知道处理完要回到原来的程序，这次可以从代码里看到原来的 `sp` 存在哪里，以及返回地址是怎么传回去的。
3. **时间片调度。** 时钟中断可以用来判断一个进程的时间片是否用完。本实验里用它做计数和设置下一次时钟事件，选择下一个进程以及切换进程上下文是后面调度部分的内容。
